# deer-flow v2.0.0 -> v2.2.0 upgrade

**Date:** 2026-11-24
**Status:** Draft for review. No code changed yet.
**Measured against:** upstream `v2.2.0` (tag `58fc5bd5`, published 2026-11-04), local clone at `deploy/deer-flow-src`.

## Why now

The 2026-09-21 drift assessment said "wait for GA". GA happened: v2.1.0 on 2026-09-24, v2.2.0 on 2026-11-04. Staying on v2.0.0 now means carrying every security fix in two releases (SSRF screening across web/browser/MCP, `DEER_FLOW_CREDENTIALS_KEY` at-rest encryption for IM and MCP OAuth tokens, authz on routes that were authentication-only, symlink/path hardening for uploads) by hand.

Our pin is not a tag we can "just bump": `deploy/deer-flow-pacgate/Dockerfile` builds `FROM ghcr.io/bytedance/deer-flow-backend@sha256:e7c503a8…` (the v2.0.0 image), the frontend overlay is copied over a `v2.0.0` clone, and 28 whole-file patches are bind-mounted over upstream sources. A naive base-image bump would silently discard or corrupt all three layers.

## The one real redesign: memory

v2.0 `storage_class` (load/save on `MemoryStorage`) is gone. v2.2.0 has `MemoryManager` (pydantic `BaseModel`) with abstract `add(thread_id, messages, *, agent_name, user_id, trace_id)` and `get_context(user_id, *, agent_name, thread_id, query) -> str`, constructed via `from_config(backend_config, *, mode=...)`, selected by `memory.manager_class` (registered backend name or dotted import path) plus `memory.backend_config`.

Proposed: rewrite `pacgate-adapters/python/pacgate_deerflow_adapter/storage.py` as a `MemoryManager` subclass pointing at pacgate-api exactly as today. Preserved semantics: matter scoping via `PACGATE_MATTER_ID`, fail-fast if unset, 409-revision `If-Match` behaviour, per-matter bucketing, the "person/org names allowed, identifiers rejected" payload rule. `get_context` returns the same formatted string the prompt expects today so the prompt patch is untouched.

Explicitly rejected: switching to upstream's `openviking` memory backend. It is single-user/owner-scoped and stores memory in OpenViking; ours is per-matter in pacgate-api with revision checking and PII refusal. Different trust boundary.

Two smaller memory patches (`deer-flow-memory-storage.py`, `deer-flow-memory-prompt.py`) are copies of upstream files carrying our edits; both get re-derived from the new upstream layout or deleted if the new `MemoryManager` absorbs them.

## Frontend overlay

20 files under `deploy/frontend-patches/files/`, including both locale bundles. v2.2.0 moved ~4,000 locale lines. The overlay mechanism (`cp -r` in `.github/workflows/build-ghcr.yml`) is all-or-nothing per file, so every overlapping file needs a hand three-way merge against the v2.0.0→v2.2.0 diff. Locale files will mostly resolve to "take upstream, re-apply our keys". The five API-route files (`app/api/sanitizer/*`, `app/api/pacgate/*`, `app/api/memory/*`) and `core/sanitizer/*` are additive and should survive with minor path/import fixes.

Risk call: `workspace-sidebar.tsx`, `workspace-sidebar-trigger.tsx`, `globals.css` all churned heavily upstream (+127 lines in globals.css alone). Budget for a real UI verification pass, not just a build.

## Upgrade / rollout risk

- Running image must be rebuilt and republished; `test-stack-version-coherence` must pass after recreate.
- Config keys silently ignored vs. rejected: v2.2.0 rejects booleans in integer config fields and rejects `system`/`developer` messages with 400. Our config must be validated with `make config-upgrade` output reviewed, not blindly applied.
- Thread deletion now cascades to runs/events/feedback. Nobody should notice, but it is a behaviour change worth one line in the release notes.
- MCP `ResourceLink` results become gated placeholders — our pacgate-mcp returns text, so no change expected; flag for verification.

## Verification (definition of done)

On a **clean temp clone**, not this box:

1. `install.ps1` from scratch; stack reaches healthy.
2. `run-all-checks.ps1` — all gates green, including `test-stack-version-coherence` (new digests), `test-baked-patch-parity` (deleted bakes gone, no stale references), `test-agent-mcp-e2e` (real agent → MCP call), `test-legal-journey`.
3. A real document run end-to-end (upload → sanitize → agent → docx out) with the v2.2.0 image.
4. Memory: write a matter fact via a run, confirm it round-trips through pacgate-api with the revision header; confirm a stale-revision write returns 409 and the agent sees the conflict rather than silently dropping.
5. Redline path (`pacgate_redline_compare`) still returns tracked changes.
6. UI smoke: workspace loads, composer submits, no console errors, locale toggle en↔zh renders our custom keys.
7. `git grep` for `tool_policy\|loop_detection\|recursion_limit` in `deploy/` — expect zero live references.

## Not doing (explicit non-goals)

- Not adopting the scheduler, multi-instance/`leader_lease`, plugin platform, or agent-teams. Single-node AIPC deployment.
- Not switching to upstream OpenViking memory.
- Not taking the opportunity to restructure the adapter package.
- No client-facing feature changes bundled in the same release.

## Suggested sequencing

1. Branch `upgrade/deer-flow-2.2.0`.
2. Memory adapter rewrite + unit tests (self-contained, reviewable).
3. Drop the 3 dead patches + config migration; boot against v2.2.0; get smoke green.
4. Re-derive remaining backend patches one at a time, each gated by a smoke run.
5. Frontend overlay merge; build; UI smoke.
6. Clean-clone verification; update `deploy/AIPC-0.2.3x-E2E-VERIFICATION.md` with results.

Rough size: step 2 ~half a day, step 3 ~a day, step 4 is the unknown (3–8 days depending on how the worker/prompt rebases fight), step 5 ~1–2 days, step 6 ~half a day. Should be its own release, not folded into 0.2.37.x.
