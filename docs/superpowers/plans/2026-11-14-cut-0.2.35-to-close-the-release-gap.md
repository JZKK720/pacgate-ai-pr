# Cut 0.2.35 to close the release gap Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `origin/main` equal to what a client actually pulls, by publishing a release that contains the one fix now stuck between them.

**The gap, measured 2026-11-14:** `v0.2.34` peels to `5956639` and every published image reports `5956639`. The redactor verdict fix `9f0e0c8` is on `origin/main` and in **no** tag from `v0.2.30` through `v0.2.34`. It touches `pacgate-ai/crates/pacgate-redact/src/{pipeline,verify}.rs`, which compile into `pacgate-api`, so it cannot travel by `git pull` or by a bind mount - only a new image carries it. Until that happens, `scripts/test-release-provenance.ps1` correctly fails, and documents blocked on model-only evidence stay blocked (397 of 868 admin-tenant chunks on this box).

**Architecture:** No code changes. A version bump, a tag or a dispatch, and then verification that the new tag and the new images agree. The only thing being built is the release the repo already has on disk.

**Tech Stack:** `scripts/bump-release-version.ps1`, `scripts/preflight-release-tag.ps1`, `.github/workflows/build-ghcr.yml`, `scripts/test-release-provenance.ps1`, `scripts/report-ghcr-digests.ps1`, `scripts/check-ghcr-anon.py`.

**Spec:** `docs/superpowers/decisions/2026-11-08-no-local-release-cut.md` (which this plan supersedes for `9f0e0c8` specifically - that decision deferred the cut to upstream, and this plan is the record of the cut happening).

## Global Constraints

- **Never move `v0.2.34`.** `scripts/preflight-release-tag.ps1` refuses to re-tag a live tag, and moving a published tag is the 0.1.28 defect `test-release-provenance.ps1` was written from.
- **Never suppress the provenance gate** to go green. No allowlist, no `-AllowUnreleased`, no skip. It is telling the truth today.
- **Do not `git reset --hard`.** This repository's own records state that doing so destroyed a fix on 2026-11-01.
- **Images are immutable.** A dispatch after a tag moves the artifacts without moving the tag. If you dispatch, the tag must be pushed from the same commit, or the gap reopens.
- **Gate exit codes: 0 = pass, 1 = real defect, 2 = CANNOT CHECK.** Exit 2 is never a pass.
- **Every claim below needs a fresh command in the same message before it is written down.** This plan exists because the previous handoff carried four stale measurements.

## Task 2: Bump to 0.2.35 and write the release note

- [ ] **Step 1: Confirm the tag and the images do not already exist**

```powershell
git ls-remote --tags origin v0.2.35
python scripts/check-ghcr-anon.py 0.2.35 pacgate-api
```

Both must show absent. A tag or image that already exists means the version was chosen wrong - pick the next free one rather than reusing it.

- [ ] **Step 2: Apply the bump**

```powershell
pwsh -NoProfile -File scripts/bump-release-version.ps1 -To 0.2.35
```

Expect 104 edits across 14 files. The script derives the pin surfaces rather than taking a file list, so a new pin file needs no edit to the script.

- [ ] **Step 3: Write the 0.2.35 release note in both READMEs**

The heading goes at the top of the release section in `README.md` and `README-ZH.md`. The note must state, in this order:

1. **What changed:** the verifier no longer treats a model-only span as proof of residue. A rule match (checksum, pattern, context) still blocks unconditionally; a model guess no longer blocks on its own. Model spans stay in residue and notes so a reviewer still sees them.
2. **What it unblocks:** documents previously blocked on model-only evidence now pass sanitization. On the dev box that was 397 of 868 chunks across four documents.
3. **What a client must do:** pull the new image and **re-sanitize** the affected documents. The verdict is computed at sanitize time and stored, so existing `blocked` rows stay blocked until re-sanitized: `POST /api/documents/:id/sanitize-rescan`.
4. **What did NOT change:** no API surface change, no schema change, no config change. This is a verdict-rule fix.

Do not reuse the 0.2.34 text. The 0.2.34 note describes the egress-admission chokepoint and the `kb_search` suppression, which are already in that release.

- [ ] **Step 4: Verify the pins agree and the tree is coherent**

```powershell
pwsh -NoProfile -File scripts/verify-delivery-state.ps1
```

Every pin must read `0.2.35`. A mixed read means a pin surface was missed.

- [ ] **Step 5: Re-render the handbooks, because the bump edits them**

`bump-release-version.ps1` rewrites the version and release-date headings inside
`deploy/AIPC-DEPLOYMENT-HANDBOOK.md` and `deploy/AIPC-DEPLOYMENT-HANDBOOK-ZH.md` (5 edits
each), so both PDFs go stale in the same commit. `test-pdf-freshness.ps1` compares COMMIT
times, so this is red until the render is committed - a later commit does not clear it.


The second pair of copies is not optional: the gate checks the `client-delivery` copies

## Task 3: Publish the images

Two paths. Dispatch is the documented preference because the tag path builds from whatever commit the tag points at. **The tag path is actually the safer one for provenance**, because it makes tag and artifact identical by construction - see Task 4, which exists because a dispatch does not.

- [ ] **Step 1: Push the bump to main**

```powershell
git push origin main
```

- [ ] **Step 2: Publish, choosing ONE of the two paths**

**Path A - push the tag (preferred here).** The workflow fires on `push: tags: v0.2.*`, checks out the tag, resolves the image tag from the ref, and labels every image `github.sha`. Tag and artifact cannot disagree because there is only one commit involved.

```powershell
git tag -a v0.2.35 -m "Pacgate AI 0.2.35 - the redactor verdict fix reaches clients" HEAD
git push origin v0.2.35
```

Check the tag is on `main` **and** equal to `origin/main` before pushing - a tag on an unmerged commit publishes images whose source no client can check out.

**Path B - dispatch (only if the tag push is blocked).** A dispatch publishes from the selected ref while accepting any `tag` input, so the two can silently diverge. If you take this path, Task 4 is mandatory, not optional.

```powershell
gh workflow run build-ghcr.yml --repo JZKK720/pacgate-ai-pr --ref main -f tag=0.2.35
```

Leave the `namespace` input empty; it resolves to the pinned `jzkk720`, which is what every compose file pins.

Record the run id and the commit it ran on:

```powershell
gh run list --workflow build-ghcr.yml --limit 1 --json databaseId,headSha,status,conclusion
```

- [ ] **Step 3: Wait for it, then confirm all six images exist**

```powershell
gh run watch <databaseId>
python scripts/check-ghcr-anon.py 0.2.35 pacgate-api pacgate-mcp ocr-service `
    deer-flow-pacgate deer-flow-frontend-pacgate laya-serve
```

Six `PUBLIC` lines. `laya-serve` is opt-in and may be absent; the provenance gate treats it as optional, so record which happened rather than assuming either.

- [ ] **Step 4: Flip any NEW package to public**

Only needed if a package name is new. All six exist already, so this should be a no-op. If a pull fails anonymously, the visibility flipped and the API `/visibility` route 404s - it is a UI action on the package settings page.

## Task 4: Tag the commit the images were built from

**This is the step that keeps the gap closed.** A dispatch publishes artifacts from a commit; it does not create a tag. Tagging a *different* commit is the 0.1.28 defect.

If Task 3 took **Path A**, this task reduces to one check - the tag is already on the built commit - and Step 2 must not be run.

- [ ] **Step 1: Read the revision the images actually carry**

```powershell
pwsh -NoProfile -File scripts/report-ghcr-digests.ps1 -Version 0.2.35
```

Note the revision label. It must equal the `headSha` recorded in Task 3.

- [ ] **Step 2: Create the tag at exactly that commit**

```powershell
git fetch origin
git tag -a v0.2.35 -m "Pacgate AI 0.2.35 - the redactor verdict fix reaches clients" <headSha>
git push origin v0.2.35
```

If `headSha` is not an ancestor of `origin/main`, stop. The build ran from a commit that is not on main, and tagging it would publish images whose source is not in the branch clients clone.

- [ ] **Step 3: Prove tag and artifacts agree**

```powershell
pwsh -NoProfile -File scripts/test-release-provenance.ps1 -Version 0.2.35
```

**Expect exit 0.** This is the gate that fails today, and it is the single objective signal that the gap is closed. It checks four things: every image shares one revision, the tag is annotated, **the tag peels to the commit the images were built from**, and no image-affecting file changed between the built revision and HEAD.

The third check was missing until 2026-11-14 - it was added after the gate was observed passing a deliberately moved tag in a throwaway clone. Do not trust an older checkout of this gate to tell you the release is coherent.

If it fails on "N file(s) that CAN reach a built image changed after the published revision was built", something landed on main after the build - re-cut rather than tagging around it.
