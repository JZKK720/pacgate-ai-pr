Annex A - Commercial Boundary Control

Scope & Delivery Matrix

This annex is the boundary map for the current clarification round. It helps both sides see what is already inside Phase 1, what still needs confirmation, and what should be handled later instead of being treated as already purchased now.

Core Rule

A question is not the same as an approved scope item

  • The client can ask about future options without those options being included today.
  • This matrix separates what is already bought from what is optional, later, or still open.
Handling Codes

How to read the handling codes

1 - Fixed delivery 2 - Advisory hours 3 - Separate quote 4 - Not supported now 5 - Pending confirmation

Commercial Sorting

Inside Fixed Phase 1

Items that should stay inside the current pilot

  • Local pilot positioning and two-system operating thesis
  • Runnable environments and deployment-support materials
  • Bounded adaptation of the two named legal-agent reference paths
  • Starter authority, knowledge, and retrieval structure
  • Initial acceptance criteria and handover materials
Requires Separation

Items that should not be mixed into fixed delivery

  • Feishu, WeChat, email, or external intake channels beyond the agreed pilot surface
  • Customer portal, multi-tenant controls, billing, and platform operations
  • Phase 2 hardware expansion and production architecture decisions
  • Full commercial legal database completion or mature GraphRAG implementation
  • Any new commercial promise not already reflected in the current quote logic

Acceptance and Payment Interpretation

Milestone Logic

Acceptance should be checked in clear layers

  • Environment layer - deployment complete and runnable in the agreed local topology
  • System 1 layer - internal-lawyer scenario demonstrated and reviewable
  • System 2 layer - prototype closed-loop scenario demonstrated with human review gate
  • Handover layer - documentation, credentials, and operating guidance delivered
Commercial Discipline

Extra support and expansion should stay measurable

  • Remote advisory should be tracked against actual consumed hours.
  • Any additional workflow, integration, or hardware expansion should be quoted separately.
  • Phase 1 exit rights should remain clear even if Phase 2 does not proceed.
附件 A - 商务边界控制

范围与交付矩阵

本附件是当前澄清轮次的边界图。它帮助双方快速看清：哪些内容已经在第一阶段内，哪些还需确认，哪些应保留到后续处理，而不应被理解成已经买下的内容。

核心原则

客户提问，不等于已经纳入范围

  • 客户可以询问未来选项，但这些内容不代表今天已经包含。
  • 本矩阵的作用，就是把已采购内容与可选项、后续项、开放项分开。
处理代码

如何理解这些处理代码

1 - 固定交付 2 - 顾问小时 3 - 另行报价 4 - 暂不支持 5 - 待确认

商务分类

属于第一阶段固定内容

应留在当前试点内的内容

  • 本地试点定位与双系统运行逻辑
  • 可运行环境及部署支持资料
  • 围绕两套命名参考系统的有限适配工作
  • Starter 级 authority、知识和检索结构
  • 初步验收标准与交接材料
必须拆开的事项

不应与固定交付混在一起的内容

  • 飞书、微信、邮件等外部接入，除非已明确纳入试点入口
  • 客户门户、多租户控制、计费与平台运营
  • 第二阶段硬件扩容与生产级架构决策
  • 完整商业法规库建设或成熟 GraphRAG 实现
  • 任何尚未在当前报价逻辑中反映的新商务承诺

问题簇矩阵

问题簇 建议处理方式 代码 回复方向
I - 项目性质、成功标准与可交付成果 在主回复和验收材料中确认 1 明确第一阶段是本地法律 AI 试点与部署支持包，而不是完整 SaaS 平台建设。
II - 详细 BOM、精确吞吐量、模型规模与后续生产服务器路径 部分待确认，部分另行报价 5 / 3 最终 BOM 应通过采购确认冻结；第二阶段工作站或服务器扩容应单独报价。
III - 部署地点、本地数据流、离线行为与远程管理员权限 通过部署附件确认 1 / 2 说明调试阶段地点、本地保留边界，以及管理员权限如何治理和关闭。
IV - Cubecloud 组件启用、授权形态与可导出性 部分确认，部分待商务澄清 1 / 5 列出启用组件，并区分可导出资产与平台依赖能力。
V - 基于 Claude for Legal 的内部律师系统 确认其 pilot 角色，并纠正“完全本地”误解 1 / 5 将其定义为内部使用的部署与适配路径，而不是无条件的本地化上游镜像。
VI - 基于 Lavern 的未来商品化路径 确认原型角色，而非产品保证 1 / 2 / 3 把 Lavern 作为原型与适配路径使用，同时把外部客户入口和生产平台工作排除在固定范围外。
VII - 共用 matter 结构、prompt 修改与每周真实场景测试 部分固定，部分顾问支持 1 / 2 共享文件与工作流纪律可纳入固定范围，但反复场景迭代和深度调优更适合走顾问小时。
VIII - Pacgate 主导法律适配与 Cubecloud 支持角色 确认 1 明确 Pacgate 主导 playbook 与法律逻辑，Cubecloud 负责部署、验证和技术排障支持。
IX - 外部法律数据库 MCP、私有 RAG、authority registry 与 context graph 确认 starter 结构，推迟成熟架构选择 1 / 5 区分外部权威检索与 Pacgate 自有知识结构，并将细粒度向量架构选择保留至后续确认。
X - 律师入口与客户入口 区分试点入口与可选扩展 1 / 2 先定义试点入口，再把飞书、邮件、微信和更强自动化接入列为可选扩展。
XI - 安全、日志、免责声明与数据出域 确认边界与可配置项 1 / 2 应通过边界表作答，而不是散点叙述。
XII - 第二阶段 SaaS 模块、预算、多租户、计费与运营 另行报价并进入后续 discovery 3 这些内容应保留为后续选项，不应通过本轮澄清自动并入第一阶段。
XIII - 验收、里程碑证据、顾问小时使用与退出权利 在商务回复包中确认 1 按系统与里程碑拆分验收，并把项目结束后的权利写清楚。
XIV - 开源许可证、修改权与商业化限制 部分固定，部分待法律确认 1 / 5 确认 Pacgate 对自身适配成果的控制权，同时保留对开源商业化约束的正式法律审查空间。

验收与付款解释

里程碑逻辑

验收应按清晰层次检查

  • 环境层 - 在约定拓扑上部署完成且可运行
  • 系统 1 层 - 内部律师场景被演示且可审阅
  • 系统 2 层 - 原型闭环场景跑通且包含人工复核门槛
  • 交接层 - 文档、账号和运行说明交付完成
商务纪律

额外支持与扩展必须可度量

  • 远程顾问应按实际消耗小时记录。
  • 新增 workflow、集成或硬件扩容应单独报价。
  • 即使第二阶段不继续，第一阶段结束后的权利也应清晰保留。
