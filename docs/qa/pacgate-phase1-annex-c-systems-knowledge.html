Annex C - Operating System Roles

Systems, Review Logic, and Knowledge Structure

This annex gives the plain-language answer to three questions: what System 1 is for, what System 2 is for, and what the knowledge layer really means in Phase 1. The short answer is that both systems are pilot paths, both keep a human review gate, and the knowledge layer is a starter structure - not a finished legal SaaS stack.

System Role Matrix

System Phase 1 role What should be demonstrated What should not be overstated
System 1 - internal lawyer workflow path Improve internal lawyer efficiency for review, drafting support, and knowledge-assisted research At least one real internal legal scenario with evidence-aware draft output and human review Do not describe it as a fully productized, fully local, ecosystem-free upstream clone
System 2 - future client-delivery prototype path Explore the future commercialization direction through a controlled prototype loop A minimal closed loop: intake, structured analysis, draft output, lawyer approval, controlled release Do not describe it as a finished commercial SaaS platform or a multi-tenant client system

Reference System Boundary Notes

Claude for Legal

Use as an adaptation reference for the internal-lawyer path

  • Cubecloud should describe this as a reference workflow path for Pacgate's internal-lawyer pilot.
  • It should not be described as a finished, fully local, self-contained product image.
Lavern

Use as a prototype and structural reference for future commercialization thinking

  • Lavern is useful as a local-capable prototype and structural reference.
  • It should not be described as an already finished commercial product.

Knowledge and Authority Structure

Layer Recommended Phase 1 position Why this matters
External authoritative legal sources Best handled through external legal database MCP or equivalent authoritative retrieval tools Helps keep primary law and update-sensitive authority outside a fragile one-off import process.
Pacgate private materials Should sit in Pacgate-controlled private knowledge and retrieval structure This is where playbooks, templates, matter files, and internal review decisions compound value.
Authority registry Phase 1 should deliver a starter structure for source tracking, version awareness, and review status Provides provenance and governance without pretending the full legal corpus is complete on day one.
Context graph Keep the initial structure light and oriented around client, matter, document, authority, agent run, and review decision relations Creates reusable schema value while leaving mature graph architecture for later stages.

Human Review and User Entry Logic

Human-in-the-loop

Remain explicit about review gates

  • Draft outputs should remain drafts until a Pacgate lawyer approves them.
  • Evidence and source distinctions should remain visible to the reviewer.
  • Customer-facing release in any prototype path should sit behind a lawyer gate.
Entry Surfaces

Keep the pilot entry surface modest

  • Phase 1 should define a practical lawyer entry point first.
  • External intake channels such as Feishu, email, WeChat, or richer forms should be treated as optional next layers.
  • The prototype should prove workflow value before committing to platform-level intake architecture.

Role Split Between Pacgate and Cubecloud

Pacgate role

Own the legal operating logic

  • Pacgate should lead legal playbooks, review standards, matter logic, and document templates.
  • These are the parts that reflect Pacgate's own legal operating identity.
Cubecloud role

Support the technical realization and operating base

  • Cubecloud should focus on deployment support, environment validation, technical tuning, and troubleshooting.
  • Its role is to provide the technical base that allows Pacgate's legal logic to run in a disciplined way.
附件 C - 运行系统角色

系统、复核逻辑与知识结构

本附件用更直接的方式回答三个问题：系统 1 用来做什么、系统 2 用来做什么、第一阶段知识层到底意味着什么。简短结论是：两套系统都只是试点路径，都保留人工复核门槛，而知识层交付的是 starter 结构，不是完整法律 SaaS 技术栈。

系统角色矩阵

系统 第一阶段角色 应验证的内容 不应夸大的部分
系统 1 - 内部律师工作流路径 提升内部律师在审查、起草辅助和知识检索方面的效率 至少跑通一个真实内部法律场景，并输出带证据意识的草稿供人工复核 不应描述成完全产品化、完全本地且无生态依赖的上游克隆
系统 2 - 面向未来客户交付的原型路径 通过受控原型闭环探索未来商品化方向 跑通最小闭环：材料进入、结构化分析、草稿输出、律师审批、受控释放 不应描述成已完成的商业 SaaS 平台或多租户客户系统

参考系统边界说明

Claude for Legal

应作为内部律师路径的适配参考

  • 更准确的说法是：它是供 Pacgate 内部律师试点使用的参考工作流路径。
  • 不应把它写成一个已经完成、完全本地、完全独立的成品系统。
Lavern

应作为未来商品化思路的原型与结构参考

  • Lavern 的价值，在于它是可本地运行的原型和结构参考。
  • 不应把它直接写成已经完成的商业产品。

知识与 authority 结构

层级 建议的第一阶段立场 为什么重要
外部权威法源 更适合通过外部法律数据库 MCP 或其他权威检索工具处理 有助于让不断更新的 primary law 保持在可靠来源，而不是依赖一次性导入。
Pacgate 私有资料 应进入 Pacgate 自控的私有知识与检索结构 这里是 playbook、模板、matter 文件和内部复核结论持续积累价值的核心。
Authority registry 第一阶段应交付 source tracking、版本意识和 review status 的 starter 结构 在不假装“完整法规库已完成”的前提下，先建立 provenance 与治理能力。
Context graph 初始结构可保持轻量，围绕 client、matter、document、authority、agent run 和 review decision 关系构建 一方面形成可复用 schema，另一方面把成熟图谱架构留给后续阶段。

人工复核与用户入口逻辑

Human-in-the-loop

应继续明确保留律师审批门槛

  • 草稿输出在 Pacgate 律师批准前，应始终视为草稿。
  • 证据与来源区别应对复核人保持可见。
  • 任何原型路径下的对外释放，都应经过律师审批。
入口面

先把试点入口收窄

  • 第一阶段应先定义一个可落地的律师入口。
  • 飞书、邮件、微信或更复杂表单等外部入口，应作为下一层可选扩展。
  • 应先证明工作流价值，再决定是否建设平台级 intake 架构。

Pacgate 与 Cubecloud 的职责分工

Pacgate 职责

主导法律运行逻辑

  • Pacgate 应主导法律 playbook、复核标准、matter 逻辑和文档模板。
  • 这些部分体现的是 Pacgate 自身的执业方法与运行方式。
Cubecloud 职责

支持技术落地和运行底座

  • Cubecloud 应聚焦部署支持、环境验证、技术调优和故障排查。
  • 它的职责，是提供支撑 Pacgate 法律逻辑稳定运行的技术底座。
