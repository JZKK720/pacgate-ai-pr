Supplementary Verbal Notes

These points remain supplementary review notes only. They do not change the current fixed Phase 1 scope, but they are now also carried in the current reply-pack revision for reference.

1. Commercial Expansion

Additional hardware is a later-scale question

The current two-machine pilot is the entry configuration, not the assumed final commercial footprint. If Pacgate later moves into a broader commercial rollout, additional hardware may be needed based on user volume, concurrency, response speed, and model size. The exact model list and configuration should be fixed at contract stage. As a directional planning number only, an additional local inference workstation is currently around the low CNY 30,000s per unit including basic application deployment labor, with higher-spec options available if larger models or heavier usage are required.

2. Access And User Volume

Broader trial use should not share the tuning lane

For Phase 1, access is intentionally controlled through the service entry rather than open workstation-side embedding. Claude for Legal depends on cloud-side API services, so it should not be treated as a locally isolated workstation component in the same way as a private local model. A broader internal evaluation - for example many lawyers trying the service at once - is possible, but it should be planned as a separate access lane or separate capacity. That avoids mixing general user testing with Lavern tuning and debugging work.

3. Feishu Test Connector

An extra connector can be tested as a bounded extension

The current standard shape is one controlled service endpoint for remote use. Adding a Feishu connector for testing is technically feasible, but it would be treated as an additional integration item rather than part of the default Phase 1 baseline. The cleaner approach is to test that connector as a bounded extension, with its own access rules and test scope.

4. Seed Client Beta

Ten-client testing starts to look like a small commercial trial

At a scale such as about 10 seed customers, the discussion is no longer only about the two-machine pilot; it becomes a small commercial trial environment. Directionally, that usually means another 2 to 3 local inference machines, each currently in the low CNY 30,000s including basic deployment labor, before choosing stronger hardware tiers. Feishu access and charging logic would add separate application and workflow work, so the final budget should be quoted after the connector flow, usage pattern, and billing method are defined.

补充口头说明

以下内容仍属于补充性的口头说明，不改变当前第一阶段的固定范围，但现已一并纳入当前版本的回函包，供参考查阅。

1. 商业化扩展

未来是否加硬件，取决于后续商业化规模

当前报价中的两台机器，是第一阶段试点的起步配置，不等于未来进入商业化后的最终硬件规模。若后续进入更大范围的商业试运行，是否需要新增硬件，主要取决于并发人数、响应速度目标、模型大小与实际使用方式。最终型号和配置应在正式合同阶段明确。若只作为方向性预算参考，新增一台本地算力工作站，目前可先按每台人民币三万出头估算，含基础应用部署与实施工费；如果选择更高性能配置，预算也会相应上升，但可以承载更大的模型和更高的并发压力。

2. 接入方式与人数

大规模体验不建议直接与 Lavern 调试环境混用

第一阶段的接入方式，原则上仍是通过受控的服务入口来使用，而不是把能力直接植入每一台工作站端。像 Claude for Legal 这类能力依赖云端 API 服务，因此不能按“本地隔离工作站内置模块”的方式来理解，否则数据边界就会变得不清晰。如果未来希望让律所更多律师同时体验，是可以规划的，但更适合单独做一条体验通道或单独配置一组容量，而不要直接与 Lavern 的调试环境混在一起。这样可以避免大规模试用影响正在进行的调参与验证工作。

3. 飞书测试端口

可以做，但更适合作为额外接口测试项

当前标准形态可以理解为一个受控服务端口，用户通过远程方式接入使用。如果后续希望增加飞书端口做测试，从技术上是可以实现的，但这更适合作为额外的接口集成测试项，而不是默认包含在当前 Phase 1 基线里。更稳妥的做法，是把飞书接入作为边界清晰的扩展测试，单独约定接入方式、权限控制和测试范围。

4. 种子客户内测

10 个种子客户量级，已接近小规模商业试运行

如果进入约 10 个种子客户量级的内测阶段，这个问题就不再只是“两台试点机器够不够”，而是开始接近一个小规模商业试运行环境。按方向性估算，通常会先考虑再增加 2 至 3 台本地算力机；目前可先按每台人民币三万出头估算，含基础应用部署与实施工费。若选择更强性能的工作站，预算会进一步提高，但也能支持更大的模型与更稳定的多用户使用。至于飞书端口和计费模式，本质上还涉及额外的接口、业务流程和计费逻辑设计，因此更适合在连接方式和计费方案明确后，另行形成专项报价。
