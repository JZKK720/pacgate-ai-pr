> 调研时间：2026年5月10日

## 一、行业背景

2026年初，法律 AI 市场正处于关键转折点：

- **闭源商业化产品**（Harvey、Legora）占据高端市场，定价高昂，主要服务顶级律所
- **基础模型能力飞速提升**（Claude Opus 4.7、GPT-5.5、Gemini 3.1 Pro），使得"薄封装层"的法律 AI 面临被巨头直接替代的风险
- **Vibe coding 浪潮**让领域专家（律师）首次有能力构建自己的工具
- **开源运动**从软件行业延伸到法律科技，挑战"高价排他"的传统模式

### 2.3 Agent 工具系统

Mike 的核心是一个基于 OpenAI function calling 格式的工具分发器。共 9 个工具：

**文档读取类：**

| 工具 | 功能 | 设计亮点 |
|---|---|---|
| `read_document` | 读取文档全文 | 自动读取最新版本（含已接受的修订） |
| `find_in_document` | 搜索文档内容 | 大小写不敏感 + 空格容错，返回上下文片段 |
| `fetch_documents` | 批量读取多个文档 | 避免反复调用 read_document |
| `list_documents` | 列出项目内所有文档 | 让 Agent 发现可用资源 |

**文档生成/编辑类：**

| 工具 | 功能 | 设计亮点 |
|---|---|---|
| `generate_docx` | 从结构化 JSON 生成 Word 文档 | 支持标题层级、法律编号、表格、横版、签名页 |
| `edit_document` | 对 DOCX 做追踪修订 | 精确 find/replace，生成 Accept/Reject 卡片，版本递增 |
| `replicate_document` | 复制文档（最多 20 份） | 批量复制模板 |

**工作流/表格类：**

| 工具 | 功能 |
|---|---|
| `read_workflow` | 加载工作流 prompt 并执行 |
| `read_table_cells` | 读取表格审查的提取结果 |

### 2.4 LLM 三层模型策略

| 层级 | 用途 | Claude | Gemini | OpenAI |
|---|---|---|---|---|
| **Main** | 高端对话/分析 | Opus 4.7, Sonnet 4.6 | 3.1 Pro | GPT-5.5 |
| **Mid** | 表格审查等批量任务 | Sonnet 4.6 | 3 Flash | GPT-5.4 Mini |
| **Low** | 标题生成等轻量任务 | Haiku 4.5 | 3.1 Flash Lite | GPT-5.4 Nano |

默认模型：Gemini 3 Flash（平衡成本与能力）。

用户在设置中自选每层模型，API Key 自带（BYOK），平台不承担 LLM 成本。

### 2.5 System Prompt 工程

Mike 的 System Prompt 约 3,000+ tokens，包含四个核心模块：

**① 引用系统（CITATIONS）**
```
回复中引用文档 → 内联 [1] [2] 标记
回复末尾 → <CITATIONS> JSON 块
每条引用：ref编号 + doc_id + page + verbatim quote
```
严格约束：只引用文档中实际出现的文本，引用保持简短（≤25词），每个引用独立。

**② DOCX 生成规范**
- 标题层级不能跳级（H1 → H2 → H3）
- 法律编号自动递进：1. → 1.1 → (a) → (i) → (A)
- 合同必须有签名页（pageBreak + 签名行）
- 前言（WHEREAS）不编号
- 生成后**强制 read_document 验证实际内容**

**③ 文档编辑规范**
- 编辑后必须重编所有受影响的编号和交叉引用
- 扫描全文枚举受影响的引用，不只看修改附近
- 不确定时宁可多改

**④ 上下文管理**
- Agent 不在对话轮次间保留文档内容
- 工具调用摘要通过 `enrichWithPriorEvents()` 注入上一轮 assistant message

### 2.6 追踪修订引擎（docxTrackedChanges.ts）

这是 Mike 最硬核的模块，约 3,000+ 行代码：

- 解析 DOCX XML（`word/document.xml`）
- 在 `<w:p><w:r><w:t>` 文本节点上精确匹配
- 使用 `fast-diff` 进行 word-level diff
- 生成标准 `<w:ins>` / `<w:del>` OOXML 元素
- 支持逐个 Accept / Reject
- 处理已有追踪修订（新编辑在已接受视图上操作）
- 兼容 Windows 反斜杠路径的 zip 文件

**编辑流程：**
```
用户上传 DOCX
  → Agent 调 edit_document（find + replace + context_before + context_after）
  → 后端解析 XML，用 fast-diff 精确定位
  → 插入 w:ins/w:del 标记
  → 生成新版本号，存到 S3
  → 前端渲染 Accept/Reject 卡片
```

### 2.7 内置法律工作流

从源码 `builtinWorkflows.ts` 提取的两个核心工作流：

**CP Checklist 生成** — 审查信贷协议，自动生成 Conditions Precedent 检查清单（横版 DOCX），按 Corporate/Financial/Legal/Security 分类。

**信贷协议摘要** — 全面法律摘要，覆盖贷款人、借款人、担保人、金额、利率、还款计划、违约条款等 11+ 个维度。

### 2.8 部署要求

```bash
npm install --prefix backend && npm install --prefix frontend
cp backend/.env.example backend/.env && cp frontend/.env.local.example frontend/.env.local
# 运行 schema.sql 初始化 Supabase
npm run dev --prefix backend && npm run dev --prefix frontend
```

必需服务：Supabase（Auth + Postgres）、S3 兼容存储、LLM API Key、LibreOffice（DOC/PDF 转换）。

### 3.4 核心功能

#### Counsel — 法律助手对话

干净的对话界面，支持快捷启动卡片（起草邮件、总结文档、编制时间线、提取控制权变更条款）。支持文件和工作流内联附加。

#### Personas — 12个执业领域助手

| Persona | 目录 |
|---|---|
| 反垄断 | antitrust |
| 仲裁 | arbitration |
| 法律商业 | business-of-law |
| 资本市场 | capital-markets |
| 劳动法 | employment |
| 知识产权 | intellectual-property |
| 诉讼 | litigation |
| 并购 | m-and-a |
| 隐私与数据 | privacy-data |
| 房地产 | real-estate |
| 税务 | tax |
| 交易 | transactional |

每个 persona 有独立的 System Prompt 和工具子集。用户可以创建自定义 persona。

#### Library — 160+ Agentic 工作流

不是简单的提示词模板，而是**工具调用的配方**（recipes）：
- 文档摘要、条款提取、起草 → DOCX 导出
- 笔录分析、监管研究
- 按执业领域分类（13个领域）
- 分页浏览（24/页），可导出 CSV
- 用户可保存自定义工作流

工作流数据存储：`prompts.ts`（106KB，约 160+ 条）、`review-templates.ts`（8KB）、`docx-workflows.ts`（8.5KB）

#### Matters — 表格审查（Tabular Review）

拖入一批文档，对每份提出相同问题。行是文档，列是问题，每个单元格是 Agent 的有据回答。支持动态添加列、导出电子表格、仅运行待处理单元格。

#### Sourcing — 可点击引用

每个回答携带内联引用，点击跳转到源文档高亮段落。杜绝编造权威。

| 意大利 | Normattiva |
| 奥地利 | RIS |
| 瑞士 | Fedlex |
| 欧洲理事会 | HUDOC |

#### Drafting — DOCX 起草

Counsel 提出目录大纲，逐节填充（同时保持相邻节的一致性），侧边面板实时渲染。可下载 Markdown 或带样式的 .docx。

#### Markups — 追踪修订红线

"从买方角度对这份 NDA 做红线批注"——Counsel 逐条款提出 Accept/Reject 卡片，侧边面板显示插入/删除，导出带原生 Word 追踪修订的 .docx。版本链是追加式的。

#### Knowledge Base — RAG 知识库（可选）

拖入文档，自动分块、嵌入、存储到 sqlite-vec。Agent 通过 `kb_search` 工具检索。

### 3.5 模型支持与配置

**默认模型：Qwen 3.6-Plus（通义千问）**

通过 DashScope 的 OpenAI 兼容 API 接入。这是一个重要信号——Suzie Law 默认使用中国模型，说明其设计考虑了非英语市场。

支持的模型路由：
- OpenAI 兼容 API（Claude、GPT、Qwen 等）
- 本地模型（vLLM / llama.cpp / unsloth）
- 多个本地端点可同时运行（Qwen 端口 8801、Gemma 端口 8802）

**配置示例：**
```
SUZIELAW_AGENT_BASE_URL=https://dashscope-intl.aliyuncs.com/compatible-mode
SUZIELAW_MODEL=qwen3.6-plus
SUZIELAW_LOCAL_QWEN_BASE_URL=http://localhost:8801
SUZIELAW_LOCAL_GEMMA_BASE_URL=http://localhost:8802
```

### 3.7 部署架构

**本地开发：**
```bash
# 1. Clone 两个仓库（必须相邻）
git clone https://github.com/firelex/open_teamsuzie

# 2. 一键启动

```

**必需服务：**

| 服务 | 用途 | 备注 |
|---|---|---|
| Node 20 | 运行时 | .nvmrc 固定版本 |
| Python 3.10+ | 文档转换 | markitdown-agent，自动创建 venv |
| SQLite | 数据库 | 零配置，文件级存储 |
| sqlite-vec | 向量检索（RAG） | 可选，与 SQLite 同文件 |
| LLM API | 智能对话 | 默认 Qwen，BYOK |

**与 Mike 的关键区别：** Suzie Law 不需要 Supabase 和 S3，使用 SQLite + 本地文件存储，部署门槛更低。生产环境可切换到 Postgres + Redis。

### 3.8 MCP 支持

Suzie Law 支持 **Model Context Protocol (MCP)**——可以通过配置文件连接外部 MCP 服务器，暴露其工具给 Agent 使用。

```env
SUZIELAW_MCP_CONFIG=./mcp.json
```

这意味着可以接入各种外部工具（DMS、日历、数据库等），扩展性很强。

## 六、对中国律师自建系统的适用性评估

### 6.1 总体判断

**Suzie Law 是更优的起点。** 原因：

1. **MIT 许可证**——无 AGPL 的开源义务约束，可自由商用
2. **模块化架构**——Team Suzie 框架层可复用于任何垂直领域
3. **默认中国模型**（Qwen）——零配置即可使用
4. **SQLite 部署**——不需要搭建 Supabase，降低运维门槛
5. **MCP 支持**——可接入中国法律数据库和内部系统
6. **Persona 系统**——可以直接创建中国法律执业领域的 persona
7. **160+ 工作流**——工作流设计模式可直接参考，本地化为中文法律场景

### 6.2 可以直接复用的组件

### 6.3 必须本地化的部分

**1. 法律检索系统**

Suzie Law 已覆盖 19 个国家但**不包括中国**。需要新增：
- 中国法律法规：北大法宝 API / 国家法律法规数据库
- 中国案例：中国裁判文书网 / 北大法宝案例库
- 可以作为 Suzie Law legal-research providers 的一个新 provider 实现

**2. Persona 本地化**

12 个内置 persona 是英美法系定位，需要新建：
- 中国诉讼/仲裁
- 中国公司/并购
- 中国劳动法
- 中国知识产权
- 中国合规/监管
- 中国房地产/建设工程
- 中国税法

**3. 工作流本地化**

160+ 工作流需要翻译和改造为：
- 合同审查清单（买卖合同、租赁合同、劳动合同等）
- 法律意见书生成
- 尽职调查报告
- 起诉状/答辩状/代理词起草
- 公司章程审查
- 合规检查清单

**4. 文档模板本地化**

9 个模板需要替换为中国法律文书格式：
- 法律意见书（中国格式）
- 律师函
- 起诉状
- 合同审查意见
- 尽职调查报告
- 诉讼代理词

**5. LLM 路由调整**

默认使用 Qwen 是好的，但需要考虑：
- DeepSeek（推理能力强）
- GLM（中文理解好）
- 通义千问（阿里云，已默认支持）
- 可能需要根据任务类型（分析 vs 起草 vs 检索）选择不同模型

## 七、行业趋势判断

### 7.1 开源 vs 闭源的法律 AI 之争

Will Chen（Mike）和 Mathias Strasser（Suzie Law）虽然出发点不同，但观点一致：

1. **基础法律 AI 应该免费**——律师不应为基本的文档分析和对话能力付费
2. **价值在于工作流，不在聊天**——单纯的 chat wrapper 没有护城河
3. **领域专家应该自己构建工具**——律师最理解自己的工作流
4. **"薄封装层"将被巨头替代**——Claude for Word、MS Legal Agent 会吃掉简单功能
5. **"厚封装层"有独特价值**——深度的、工作流驱动的、高度利用率的系统会存活

### 7.2 对中国法律科技市场的启示

1. **开源降低了进入门槛**——中小律所不再需要为 Harvey 级别的能力支付高昂费用
2. **本地化是关键差异化**——谁先做好中国法律检索 + 中文法律工作流，谁就有市场
3. **MIT 许可证鼓励商用**——Suzie Law 的 MIT 许可比 Mike 的 AGPL 更适合商业化
4. **BYOK 模式值得借鉴**——平台不承担 LLM 成本，用户自带 API Key
5. **"基础免费 + 增值收费"可行**——Scissero 的模式在中国也可复制

## 八、结论与建议

**核心结论：** Suzie Law 在架构设计、功能完整性、部署灵活性和许可证友好度上全面优于 Mike，是中国律师自建 AI 系统的最佳起点。但 Mike 的 Agent 工具系统和追踪修订引擎在代码实现上更为成熟，值得选择性借鉴。

3. **中期**：开发中国法律检索 provider，完善中文法律能力
