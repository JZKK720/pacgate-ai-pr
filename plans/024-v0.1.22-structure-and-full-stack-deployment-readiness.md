### Answers this evidence already gives

1. **Has upstream completed the v0.1.22 building structure?** Yes at the
   artifact level: Cargo version, both compose pin sets, five public GHCR
   publishes, aligned docs (README / handbook / SETUP-AND-OPERATIONS at 0.1.22).
   The no-git-tag gap has been **RESOLVED as a decision, not by creating a tag**
   (Task 1, executed 2026-10-04): the five images were proven via their OCI
   revision labels to be built from exactly one commit — `95a6418`, the
   `release: 0.1.22` commit on `origin/main` — through the workflow-dispatch
   route, which `build-ghcr.yml` documents as the preferred release path. A
   back-dated tag was rejected because pushing a `v0.1.*` tag triggers a fresh
   GHCR build with its own commit context — a release action, not a
   verification action. Provenance now keys on the image revision labels
   (E9), which are strictly stronger than a tag: they name the exact commit
   each binary was compiled from. If the maintainer still wants a tag for
   tooling convenience, that is a follow-up commit on its own.
2. **Are the full stacks ready for deployment?** Structurally yes (Task 2
   verifies the compose map end to end); on *this machine* the stack is not
   currently deployed and three gates must still pass: `.env` provisioning +
   bring-up (Task 3), the Ollama model roster (Task 4, blocker), and the qm
   sandbox (Task 6, carried **HIGH** defect).
3. **OpenViking persistent memory ("second brain")?** Shipped as the fifth
   container pinned by digest (`ghcr.io/volcengine/openviking@sha256:46f9e34c…`),
   port 1933, `root_api_key` rendered from `OPENVIKING_ROOT_API_KEY`, state
   persisted via the `./openviking:/app/.openviking` volume. deer-flow reaches it
   via MCP; qm via the ov-remember/ov-search/ov-read bridge. Task 5 verifies
   health, auth, a write→search→read round-trip, tenant headers, and persistence
   across a container recreate.

## Architecture decisions

- **Reuse the repo's own gates before writing new probes.** `smoke-full-stack.ps1`,
  `run-all-checks.ps1`, `test-workflow-library-served.ps1`, `test-memory-lane.ps1`,
  `test-model-roster-consistency.ps1`, `check-ghcr-anon.py` already encode the
  repo's lessons (derived version marker, in-network health probes, parse-don't-
  substring). A new ad-hoc probe contradicts them.
- **Verification on the dev box uses the tracked `compose.prod.yaml` pins**, not
  `compose.bundle.yaml`, so results match the client install surface. OCR
  enablement uses the existing `compose.ocr-override.yaml` (dev-box intent).
- **No fix work in this plan.** The qm sandbox defect and the 500-vs-422 defect
  stay scoped to their own DEFECT files; this plan only measures and reports.
