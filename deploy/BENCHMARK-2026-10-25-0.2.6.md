## 8. Memory lane

| Operation | Latency | Payload |
|---|---|---|
| `load()` | **12 ms** | 65 facts |
| `save()` | **35 ms** | 65 facts, no loss |

- Storage class resolves to `PacgateMemoryStorage` (a real `MemoryStorage` subclass)
- Bound to matter `8f963544-4408-47c7-9817-d95c89e0d140`
- `GET /api/matters/{id}/memory` -> HTTP 200 with the deer-flow shape
- **No fallback warning in 3 h of logs**

### Caveat worth knowing

`get_memory_storage()` falls back **silently** to `FileMemoryStorage` on any
exception, logging only at error level. A genuine misconfiguration would degrade
the memory lane to local files with no visible failure.

**Fixed 2026-10-25.** `deploy/client-bundle/patches/deer-flow-memory-storage.py`
now refuses that fallback: if a storage class WAS configured and cannot be built,
it raises instead of substituting `FileMemoryStorage`. Falling back is allowed
only when nothing was configured, which is the honest default.

The reason this matters is not cosmetic. `PacgateMemoryStorage` writes matter
memory through `pacgate-api`, so it inherits the sanitization gate.
`FileMemoryStorage` writes plaintext JSON to the local filesystem - outside the
gate, outside the audit log, and invisible to every health check. The stack would
report healthy while the memory lane had quietly left the sanitized path.

The fallback is reachable by a plain initialization-order mistake: calling
`get_memory_storage()` before `get_app_config()` reads the module-level default
`MemoryConfig()`, whose `storage_class` is `FileMemoryStorage`, so the configured
class is never even attempted. That is exactly the shape of bug that survives a
green suite.

`test-memory-lane.ps1` now asserts the runtime behaviour, not just the config:
it checks the patch is mounted, then breaks the configured class in-process and
requires a raise. Red-checked by unmounting the patch - the gate fails with
`exit 1` and both runtime checks red.

## 10. Regressions found

**None.** All 24 area gates and all 51 suite gates pass.

One defect was found and fixed during this audit:

**The memory lane could degrade silently.** `get_memory_storage()` fell back to
`FileMemoryStorage` on any exception, logging only at error level. That would
move matter memory off the `pacgate-api` sanitization gate while every health
check still reported green. Now patched to raise when a storage class WAS
configured, and `test-memory-lane.ps1` asserts the runtime behaviour rather than
only the config. See section 8.

Two things that look like regressions but are not:

1. **`test-release-provenance.ps1` reports SKIP (exit 2) inside the suite.**
   Exit 2 is CANNOT CHECK, not a failure - a transient ghcr.io TLS drop. It
   passes standalone (exit 0) and the suite treats exit 2 as non-failure.

2. **deer-flow's agent has 0 skills.** qm's has 3. This is a recorded decision,
   not a regression: `deploy/AUDIT-2026-10-14-v0.1.29.md` states skills are
   *"Not a product surface ... Nothing to test."* The 35 MCP tools carry the
   full surface, which is why 8/8 generation runs pass with zero skills.
