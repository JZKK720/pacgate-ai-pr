# Clearing this dev machine — what is safe to destroy, and what is not

**Answered:** 2026-10-04, before any destructive command was run.
**Question:** the new dev machine is pulling everything; can this box's containers,
stacks and caches be cleared?

## Is the code, automation and workflow library on this machine only? — NO

Every one of these is **tracked in git and pushed** (0 unpushed commits on any
branch, clean tree). Verified by count, not by assumption:

| Asset | Where it lives | Tracked |
|---|---|---|
| `pacgate-api` source | `pacgate-ai/crates/pacgate-api` | **18 files** |
| `pacgate-mcp` source | `deploy/pacgate-mcp` | **3 files** |
| automation / gates / probes | `scripts/` | **92 files** |
| CI workflow | `.github/workflows/` | **1 file** |
| client-bundle workflows | `deploy/client-bundle/workflows/` | **15 files** |
| workspace workflows | `pacgate-ai/workflows/` | **15 files** |
| prompt templates | `docs/prompt-templates/` | **1 file** |

**"222 workflows" is not 222 files — it is 220 YAML entries plus 2 code-defined
built-ins.** Verified end to end rather than asserted:

1. Each YAML is a **list of workflow objects**, one per top-level `- id:` entry.
   Counting those unique IDs gives **220**:

   ```
   litigation_extra 49   compliance_extra 28   fund_extra 27
   nonlitigation_extra 25   daily_general 24   compliance_specialized 10
   archive_collection 10   litigation 9   banking_general 8   fund_lawyer 6
   capital_markets 5   contract_review 5   investment_financing 5
   ma_due_diligence 5   compliance_corporate 4
   ```

2. The live API serves **222**. Diffing the served IDs against the YAML IDs leaves
   exactly two, which no YAML defines:

   ```
   00000000-0000-0000-0000-000000000101  Contract Review      contract_review
   00000000-0000-0000-0000-000000000102  Contract Comparison  contract_review
   ```

   These are **built into the Rust code**, not shipped as files. So the served
   library = 220 from the bind mount + 2 compiled in.

My first phrasing called them "built-ins" without checking, which was a guess that
happened to be right. The diff above is what actually establishes it.

**Why this matters for clearing:** the two code-defined ones live in the
`pacgate-api` image, and the 220 live in git. Neither lives only here.

They are **bind-mounted**, not baked into a volume:

```
deploy/client-bundle/workflows -> /app/workflows    (pacgate-api)
```

so a container wipe does not touch them; they come from the repo.

### Also shipped inside the images, as well as in the repo

`pacgate-api`'s image contains the same 15 workflow YAMLs at `/app/workflows`
(checked: 15 present). So the library exists in **two** places — git and the GHCR
image — and the mounted copy simply overrides the baked-in one. Neither is
machine-local.

### Two runtime files exist ONLY here, and are reproducible

| File | Tracked? | Reproducible from |
|---|---|---|
| `deer-flow-extensions-config.json` | no — rendered | `…template.json` (tracked) |
| `openviking/ov.conf` | no — rendered | `ov.conf.template` (tracked) |

Both are rendered by `install.ps1` (the `$ovTemplate` / `$dfTemplate` paths), so
they regenerate on a fresh install. `deer-flow-config.yaml` is tracked outright.

**Net: nothing about the code, automation, workflows or templates is at risk.**
The only true machine-local assets remain the two `.env` files below.

## Verdict

**Containers and build cache: safe. Volumes: safe for the pacgate stacks, but do
NOT use `docker system prune --volumes`.**

## What was checked, and the answers

### 1. Is there irreplaceable client data? — NO

`client-bundle_pacgate-db-data` holds **415 matters**, which is the number that
makes this worth checking before deleting anything. Inspected:

| Check | Result |
|---|---|
| Sample names | `E2E Sanitizer Test`, `Debug E2E`, `Sanitizer E2E`, `journey-*`, `emptygate-*`, `txtnative-*`, `default` |
| Creation pattern | bursts of **5 per minute** — repeated E2E runs |
| Real client matters | **none — verified explicitly, see below** |
| Documents | 27 across 23 matters — all from the same test runs |
| `deploy/client-bundle/data/` | 43 files, 8.5 MB — bind mount, gitignored, test fixtures |

The name-pattern filter left **one** unmatched matter, so it was inspected rather
than assumed: `OCR Surface Probe` (2026-09-19, 2 documents) — a diagnostic matter
created by an OCR probe script, i.e. test debris under a name the filter did not
anticipate. `Firm Knowledge Base` holds **0 documents**.

So the database is **test debris**, not client material. Deleting it loses nothing
that cannot be regenerated by running the gates.

The exact query used, so it can be re-run rather than trusted:

```sql
SELECT count(*) FROM matters
WHERE name NOT ILIKE '%test%' AND name NOT ILIKE '%e2e%'
  AND name NOT ILIKE '%journey%' AND name NOT ILIKE '%emptygate%'
  AND name NOT ILIKE '%txtnative%' AND name NOT ILIKE '%debug%'
  AND name NOT ILIKE '%smoke%'
  AND name <> 'default' AND name <> 'Firm Knowledge Base';
-- returns 1: 'OCR Surface Probe'
```

### 2. What CANNOT be regenerated — the `.env` files

Both are gitignored with **0 commits in history**, so a wipe destroys them
irreversibly:

- `deploy/client-bundle/.env` (1849 bytes)
- `deploy/client-bundle/qm-pacgate/.env` (1532 bytes)

`install.ps1` **exits 1** if `.env` is absent, so this machine would not reinstall
without them. Several values are machine-generated (`OPENVIKING_ROOT_API_KEY` and
`PACGATE_API_PASSWORD` are 32-char generated values), so they cannot be guessed
back.

**Back these up before clearing anything.**

### 3. The real hazard: 15 OTHER projects share this Docker daemon

Docker is machine-global. `docker system prune --volumes` would destroy:

```
ai-memory            hermes-postgres      odysseus-odysseus-1
axiom-quant-topology hermes-web           odysseus-searxng-1
business-site-*      kedios-b300-topology open-webui
cloudflare-tunnel    neoway-legal-web     dockhand
hermes-gateway       odysseus-chromadb-1
```

Their volumes (`hermes-agent_postgres_data`, `odysseus_chromadb-data`,
`ai-memory-data`, `open-webui`, `dockhand-dash_dockhand_data`, …) are unrelated to
pacgate and would be lost with no warning.

## What is actually reclaimable

```
Images          38.86GB    118.3MB reclaimable (all images are in use)
Containers      152.2MB    4 KB
Local Volumes   1.643GB    0B reclaimable (all in use)
Build Cache     20.53GB    14.4GB reclaimable   <-- the only real win
```

**14.4 GB, essentially all of it build cache.** Pruning volumes frees ~0 because
every volume is attached to a running container.

## Recommended commands

```powershell
# 1. FIRST: back up the two .env files somewhere off this machine.
#    install.ps1 exits 1 without them, and they are untracked + ungeneratable.

# 2. Stop only the pacgate stacks (leaves the other 15 projects alone).
cd deploy/client-bundle
docker compose -f compose.prod.yaml down          # NO -v: keeps the volumes
cd qm-pacgate
docker compose -f compose.qm.yaml down            # NO -v

# 3. Reclaim the real 14.4 GB. Safe: build cache holds no data.
docker builder prune -f

# 4. If the volumes are genuinely wanted gone (test debris only, per above):
docker volume rm client-bundle_pacgate-db-data client-bundle_paddleocr-models
docker volume rm qm-pacgate-coredata qm-pacgate-pgdata pacgate-ner-models

# 5. Remove only the pacgate images, by name. NEVER 'docker system prune'.
docker rmi ghcr.io/jzkk720/pacgate-api:0.1.22 ghcr.io/jzkk720/pacgate-mcp:0.1.22 `
          ghcr.io/jzkk720/ocr-service:0.1.22 ghcr.io/jzkk720/deer-flow-pacgate:0.1.22 `
          ghcr.io/jzkk720/deer-flow-frontend-pacgate:0.1.22
```

**Never run:** `docker system prune -a --volumes`. It is machine-global; it would
take the other 15 projects' data with it, and it frees nothing worth the risk
since no volume is reclaimable anyway.

## Two honest caveats

1. **`paddleocr-models` is a large re-download.** It is regenerable (the container
   re-pulls weights on boot), but it costs bandwidth and time. Keep it if the
   machine may be used again soon.
2. **This box has been the reference environment** for the 0.1.22 audit and the
   sandbox investigation, and it is the only place the sandbox image is cached
   locally. Nothing in git or GHCR is lost, but a full wipe means the next
   investigation starts by re-pulling everything.
