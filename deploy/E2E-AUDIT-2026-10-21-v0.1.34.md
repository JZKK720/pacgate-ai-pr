# End-to-end audit — Pacgate-ai 0.1.34 (true e2e, evidence per lane)

**Date:** 2026-10-21
**Artifact:** `0.1.34`, revision `8adb4818e7e5`, all 5 images public
**Machine:** HX370 dev box (`CUBECLOUD01`) — 61.6 GiB RAM, RX 7600 XT 16 GB,\
Windows PowerShell 5.1 (no `pwsh`)
**Question this document answers:** *did the stack actually RUN, end to end, on
every lane — or was it only reachable?*

**Method.** Every lane below was exercised by **writing state and reading the
effect back from a different surface**. Where a lane could not be proven, it says
so with the reason. Nothing here is inferred from a health probe.

> **Scope correction.** This supersedes the "smoke test" claims in
> `AUDIT-2026-10-21-v0.1.34.md`. That earlier pass established *reachability and
> contract shape*. It did **not** write a document, execute a workflow, or prove a
> memory round-trip. This document does.

## 2. OCR lane — honest partial

`ocr-service` is healthy, its PaddleOCR weights are baked (`det` + `rec` + `cls`),
and the smoke lane confirms the module imports against the baked tree.

**But the upload route rejects `.png`:**

```
400 {"error":{"code":"bad_request","message":".png is not a supported format.
     Supported: .docx .xlsx .pptx .pdf .txt .md .html"}}
```

So the *image → OCR → text* path cannot be driven through the public document
API. OCR is reachable and configured; it is **not exercised end-to-end by a
client upload** on this artifact. Marked PARTIAL rather than claimed.

> **2026-10-21 update:** the allowlist and the OCR call's filename were both
> fixed in source after this measurement (see
> `MODEL-REGRESSION-AND-CAPACITY-2026-10-21-v0.1.34.md` §3). The block above
> records what the *deployed* 0.1.34 image did; re-run this lane after the next
> image build.

A scan-only PDF is the closest legitimate path, and that leads directly to §3's
important result.

## 3. Workflow execution and document generation — PROVEN, and a guardrail worth keeping

Ran `contract_review` (`00000000-…-0301`) against a matter holding a readable
`.md` supply agreement:

| Step | `tool` | `tools_used` | rounds capped |
| --- | --- | --- | --- |
| Read contract | `read_document` | `list_documents, read_document, find_in_document, kb_search` | False |
| Find risk clauses | `find_in_document` | `list_documents, kb_search, read_document, find_in_document` | False |

**Document rows: 1 → 2.** The new row is
`Supply_Agreement_Review_Memo.docx v1`. Generation is proven.

### The same workflow against a PDF with no text layer REFUSED

Run earlier against a hand-synthesised PDF, the agent **refused**:

```
read_document -> storage error: PDF has no native text layer in this store;
                 use the OCR/convert lane
final_content -> "合同审查备忘录 — 无法出具（文档无可提取文本）"
```

That is the guardrail working: it declined to invent a contract review over
unreadable input, and said why.

> **This corrects a conclusion in `AUDIT-2026-10-21-v0.1.34.md` §7.4.** The
> `test-document-generation-e2e` failure recorded in plan 027 was caused by the
> **test document having no native text layer**, not by a broken generator. With a
> readable document, generation succeeds and persists.

## 6. openviking — write / store / memories, PROVEN (and slow)

`remember` is **asynchronous**. The reply is explicit:

```
Stored 1 message(s) and committed for memory extraction.
```

The container log confirms the extraction worker running:

```
LiteLLM completion() model= gemma4:12b-it-qat; provider = ollama
```

Final proof — a fact written via `remember`, paraphrased by extraction, and
retrieved by `find`:

```
find('PROJECTOAUTH') -> 200, present=True
  - Internal project codename is PROJECTOAUTH1792560473 (Q4 litigation matter).
```

The memories tree still shows only three files (`identity.md`, `profile.md`,
`soul.md`) because extracted facts land in the searchable index rather than as
siblings of those root documents — so **`find` is the surface to verify with, not
`list`**.

**Latency matters operationally:** the round-trip took **minutes**, because
extraction runs through the local 12B model on a single Ollama runner slot. A
probe that checks `find` immediately will report a false negative, which is
exactly what my first attempt did.

## 7. Findings

### F1 — `remember` returns HTTP 200 *and* `isError:false` while the tool call failed *(MCP client hazard, medium)*

Calling `remember` with `content` instead of the schema's required `messages`
produced:

```
HTTP 200
result.isError = false
text = "Error executing tool remember: 1 validation error for rememberArguments
        messages  Field required"
```

A client that trusts the status code or `isError` records a **broken tool call as
a success**. Tool-level errors arrive as *text*. Clients must inspect the payload.

### F2 — `test-lane-connectivity.ps1` E2 can pass by testing the wrong service *(gate defect, medium)*

E2 probes host ports `8090/8091/8088` for `/` or `/health`. `pacgate-mcp` publishes
**no host port**, and **`8090` is `deer-flow-frontend`**, which answers `/` with
200. E2 therefore passes by talking to the frontend. Same class as the E10 5.1 bug
fixed in `a43d87c`.

### F3 — `test-skills-and-templates.ps1:151` fails under Windows PowerShell 5.1 *(gate defect, medium)*

```
docker : template parsing error: template: :1: unexpected "|" in command
  $mounted = docker inspect $qmCore[0] --format '{{range .Mounts}}{{.D...'
```

The Go template contains `|`, which PowerShell 5.1 mangles before docker sees it.
This is precisely the bug class that `a43d87c` fixed for E10: a reporting/probing
step that takes the whole gate down instead of degrading. The **static** checks
K1/K2-passed; only the live mount check dies.

### F4 — `.png` uploads are rejected, so the OCR lane has no client path *(documentation, low)*

**FIXED IN SOURCE 2026-10-21 (not deployed).** The accepted set was
`.docx .xlsx .pptx .pdf .txt .md .html`; OCR was wired and healthy, but a client
could not submit an image through `/api/documents`. Raster extensions are now
accepted and routed to the OCR lane - see `MODEL-REGRESSION-AND-CAPACITY-2026-10-21-v0.1.34.md`
§3. Deploying needs a version bump or an explicit local-tag override.

### F5 — `remember` → retrievable memory takes minutes on a local model *(operational, low)*

Extraction is LLM-backed. On this box that is the local 12B on one runner slot, so
a freshly remembered fact is not findable for minutes. Any e2e that asserts
immediately will produce a false negative.

### F6 — Mutation gates leave tracked files mutated on failure *(carried forward, high)*

Unchanged from plan 027, re-checked here: **CLEAN**. When a `*-mutations.ps1` gate
fails, the restore never runs and the tree keeps real mutations — including
`deer-flow-config.yaml` reverted to the *unsanitized* `FileMemoryStorage`. Always
`git status --porcelain deploy/client-bundle/` after a suite run.

## 8. My own measurement errors (recorded so they are not repeated)

Each of these produced a **false negative** that I nearly reported as a product
failure:

| # | Mistake | Symptom | Truth |
| --- | --- | --- | --- |
| 1 | Omitted `Authorization` on POSTs | 401 on matter create / upload | client bug |
| 2 | Read login token from `access_token` | every authed route 401 | field is **`token`** |
| 3 | Read only the 1st SSE `data:` line | "0 MCP tools" | **19** tools |
| 4 | Read `name`/`ok`/`rounds` from workflow steps | all `None` | fields are `step_name`/`tool`/`tools_used`/`max_rounds_reached` |
| 5 | Guessed openviking arg names (`content`, `path`) | tool errors hidden in text | `messages`, `uri`, `uris` |
| 6 | Expected `find` to be synchronous | "marker not found" | extraction is async, minutes |
| 7 | Invented placeholder `[PHONE_1]` for restore | 400 refusal | must reuse the **issued** placeholder |
| 8 | Uploaded `.png` to exercise OCR | 400 unsupported format | OCR has no client upload path |
| 9 | Hand-built PDF with no text layer | workflow refused, no document | **correct guardrail**; use a readable doc |
