## 2. `/initialize` — CORRECTED. The previously recorded fix was wrong.

**Status:** open, but the fix is now known to be a **two-part** change.

The defect note previously described arming `PACGATE_SETUP_TOKEN` as a one-line
config change. **It is not, and doing only that would break first-run setup.**

The frontend posts email + password and **no token**:

`deploy/deer-flow-src/frontend/src/app/(auth)/setup/page.tsx:75`

No setup-token input exists in the UI (0 hits for `setup_token` / `setupToken` /
`PACGATE_SETUP` across the frontend and the frontend patches).

### Proof (gate armed via temporary compose override, then reverted)

| Condition | Request | Result |
|---|---|---|
| gate **unarmed** (shipped) | UI payload, no token | `409 system_already_initialized` |
| gate **armed** | UI payload, no token | **`403 setup_token_required`** |

The token check runs **before** the admin-count probe (deliberately, so an
unauthenticated caller learns nothing about whether an admin exists), so arming
converts 409 → 403. On a **fresh** install that means the first admin can never be
created through the UI. Arming the gate alone replaces a claimable-admin window
with an **unbootstrappable install**.

**Required fix:** provision the token **and** teach the setup page to send it.
Full detail: `deploy/DEFECT-initialize-bootstrap-token.md`.

### Second finding recorded in the same note

`install.ps1` step 6a bootstraps the admin with `POST /api/auth/register`, but
that route creates `system_role="user"` only and ships
`allow_registration: false`, so it is refused (**403**, confirmed by
`scripts/test-auth-registration-gate.ps1`) and the installer merely warns and
continues. pacgate-api's user store therefore ends up with **no admin**.
Different service and user store from the deer-flow `/initialize` issue.

## 5. Defect found and fixed DURING this audit

**The client-facing ZH handbook PDF was three versions stale.**

`deploy/AIPC-DEPLOYMENT-HANDBOOK-ZH.pdf` still advertised **0.1.19** while its own
source said **0.1.21** — verified by extracting the PDF text, which contained no
`0.1.21` anywhere. The 0.1.21 bump rewrote the `.md` and the render was never
regenerated.

This is precisely the failure `test-pdf-freshness.ps1` exists to catch, and the
gate did catch it in the suite run.

**Why it was nearly missed** — worth recording, because it is a trap:
`test-pdf-freshness-mutations.ps1` rewrites **that same PDF** as its fixture. So
running that mutation suite as a standalone step *refreshes the render mtime* and
hides the staleness; the gate then passes and looks fine. The runner caught it only
because it executes the gate **before** its own mutation suite. **Never run the
mutation suite to check the gate it mutates — run the gate.**

Fixed by re-rendering with the command the gate itself prescribes:

```
.venv/Scripts/python.exe safe_markdown_to_pdf.py <src.md> <out.pdf>
```

…then re-syncing `deploy/client-delivery/docs/`. Those two were byte-identical at
HEAD (`0e536830`), so per the gate's own rule drift between them is a defect, not
a different document.

**Coverage note:** the gate compares **mtimes**, and its header states plainly that
this "cannot PROVE freshness" — a re-touch without a re-render passes. A content
check (extract PDF text, assert the source's highest version appears) would catch
that class independently. None is committed; the check used here was ad hoc.
