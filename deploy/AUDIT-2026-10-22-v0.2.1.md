## 1. Sanitizer

### 1.1 What is correct

The pipeline order in `pacgate-redact/src/pipeline.rs` is
DETECT → DECIDE → REPLACE → VERIFY → seal, and the ordering is load-bearing:
`verify_reduced` re-runs the *same* detector set over the redacted text, so a
replacement that fails to remove a span is caught rather than trusted.

`verify.rs` is fail-closed on both degenerate inputs:

- an **empty detector set** returns `Block`, not `Pass` — otherwise a
  misconfigured `PACGATE_NER_MODEL_DIR` would silently certify raw text;
- a **detector error** returns `Block`, not `Pass`.

`policy.rs` returns `allow_auto_pass: false, require_human_review: true` for T4
unconditionally, even on a clean verdict.

`reingest_sanitized_chunks` (`pacgate-rag/src/ingest.rs:205`) deletes and
re-inserts the chunks in **one transaction**, so a promotion cannot leave a
document labelled `sanitized` while its `content` still holds raw text. That
delete-then-insert is the fix for the 0.1.28–0.1.30 leak documented in
`DEFECT-sanitized-content-not-served.md`, where the flag was flipped without
rewriting the text and the RAG gate served the raw chunks.

The ledger row is written **before** promotion, so a crash between the two
leaves a document at `pending` with evidence, never `sanitized` without it.

### 1.2 Defect — T4 was reported but never enforced (HIGH, fixed)

`sanitize.rs` promoted on `verdict != block` alone:

```rust
let promoted: u64 = if verdict_is_block { /* blocked */ } else {
    ingestor.reingest_sanitized_chunks(...)   // <- unconditional
};
```

`outcome.decision.allow_auto_pass` was carried into `JobOutcome` and returned to
the caller, but never consulted. Consequence: a **T4** document with a clean
verification was marked `sanitized`, which clears the download egress gate in
`documents.rs:220-235` and the RAG gate in `build_filtered_sql`. That is exactly
the auto-pass the design forbids:

- `docs/superpowers/specs/2026-09-18-sanitizer-agent-design.md:327` — "T4 …
  elevated checks, HITL, no auto-pass"
- same file, line 501 — "escalate to HITL, not auto-pass"

No approval endpoint exists anywhere in the router, so the `require_human_review`
flag had no consumer at all.

**Fix.** A clean verdict now also requires `allow_auto_pass`. When policy refuses,
the document is **left at `pending`** and nothing is written:

- `pending` is the fail-closed state — the RAG gate and the download gate both
  refuse it, and it is the only state a future approval can promote from;
- no new state, so **no migration** and no egress-gate change;
- the hold branch issues **no SQL at all**. A `pending → pending` UPDATE would
  be a no-op that only looks like enforcement, so the branch returns `0` and the
  gate test asserts the absence of a write rather than the presence of one;
- the raw chunks are left untouched, so nothing is rewritten for a document that
  is not being released;
- the audit row now records `disposition` (`blocked` / `held_for_review` /
  `sanitized`) alongside the verdict, so "pass but held" is distinguishable from
  "pass and released" in the audit trail.

Two gate tests were added: `a_held_document_stays_pending_and_never_promotes`
(asserts the hold branch contains no `sqlx::query`) and
`promotion_requires_policy_consent_not_just_a_clean_verdict` (asserts the hold
branch precedes the promotion call in source order).

**Open product question.** `pending` was chosen over a new `pending_review`
state because it needs no schema change and fails closed. If the review panel
needs to *list* held documents, a distinct state is the better answer and this
should be revisited — the current design cannot distinguish "never processed"
from "processed and awaiting a human".

### 1.3 Residual — `chunks_promoted == 0` is not surfaced as a failure

`reingest_sanitized_chunks` returns the chunk count and `run_job` stores it in
`promoted`. A `0` means "there were no chunks to rewrite", which is legitimate
for a document ingested before chunking existed, but it is also what a silent
rewrite failure would look like. Not changed: the correct behaviour depends on
whether a zero-chunk document should be promotable at all, which is a product
decision, not a bug fix.

## 2. OCR

### 2.1 What is correct

`deploy/ocr-service/app.py` fails closed on all four degenerate paths, each
returning `incomplete` rather than an empty-but-successful result:

1. empty result list;
2. empty `result[0]`;
3. zero text spans;
4. rasterisation failure.

`incomplete` is the right signal because `extract.rs` reconciles on
`incomplete || text.trim().is_empty()`, so a page that yields nothing cannot be
mistaken for a page that was read and found blank.

The PP-OCRv4 det/rec/cls weights (~17 MB) are **baked into the image at build
time** and the compose files mount no volume over the weights directory, so a
runtime download cannot shadow them. This is the fix for
`DEFECT-ocr-weights-not-baked.md`, where a first-extraction download made the
OCR lane the one service needing an external host.

The cache is keyed on `document_extractions`, **not** on span emptiness. Keying
on spans would re-OCR a text-free page forever while still being unable to
record that it was incomplete — the cache key has to be "did we attempt this
version", not "did we get text".

### 2.2 No defect found — but the fail-closed logic was untestable

The filename-extension forwarding fix is present: the OCR call passes the
original extension, so a `.png` is not rasterised as a `.pdf`. Text-native
formats (docx/xlsx/pptx/html/markdown/txt) route to `text_extract` and never
reach the OCR service.

The four fail-closed paths were correct but **inline in the endpoint**, so
proving them required PaddleOCR, the baked weights, and a container. That is why
the previous audit could only assert them by reading the code.

**Change (behaviour-preserving, plus one deliberate hardening).** The decision
moved into `_page_spans(page_no, result) -> (spans, complete)`, which is pure.
`deploy/ocr-service/test_app.py` now pins all four shapes with 22 assertions and
needs no OCR stack — it stubs `fastapi` the same way
`scripts/test-mcp-401-retry.py` stubs the MCP SDK.

One deliberate behaviour change: a **malformed OCR line** is now skipped instead
of raising. Previously a single bad line aborted the whole request with a 500,
losing every good line on the page. Now the line is dropped, and if that leaves
the page with no spans the page is still reported `incomplete` — so the
hardening cannot turn a partial read into a false complete.

Mutation-tested: flipping `return [], False` to `return [], True` fails 5
assertions.

## 3. Matter memory

### 3.1 What is correct

`memory_scope.rs` enforces the lane rule — *memory holds process, not matter
facts* — with Tier-1 detectors only (`CnResidentId`, `Uscc`, `CnMobile`,
`BankCard`, `Email`) and a 64 KiB cap. `PersonName`, `OrgName` and `Location`
are **deliberately allowed**: a process summary that cannot name the client is
useless, and the scope gate is not a redactor.

The scope check runs **before any filesystem access** in `save_matter_memory`,
so an out-of-scope payload cannot create a directory or a file as a side effect
of being rejected.

`write_atomic` writes to a temp file, `sync_all`s, then renames — a reader sees
either the old file or the new one, never a truncated one. The revision counter
is **server-owned**: the client sends `If-Match` and the server decides the next
value, so a client cannot rewind or skip a revision.

The adapter distinguishes **409** (revision conflict — retry with the current
revision) from **422** (out of scope — the payload is wrong, retrying will not
help). Collapsing those two into one status would make an agent retry a
permanently rejected write.

### 3.2 Defect — the MCP memory write was dead (HIGH, fixed)

`deploy/pacgate-mcp/server.py` called:

```python
client.post(f"/api/matters/{matter_id}/memory", json=..., headers=headers)
```

but `PacgateApi.post()` had no `headers` parameter. Proven by execution:

```
TypeError: PacgateApi.post() got an unexpected keyword argument 'headers'
```

Every `pacgate_write_memory` call failed, and the `If-Match` revision guard the
tool advertises was unreachable from MCP. The sibling adapter
`deploy/client-bundle/patches/pacgate-adapter-client.py` already carries the
correct signature with a comment naming this exact `TypeError` — the same bug
was fixed there and missed here.

**Fix.** `post()` now accepts `headers` and forwards them to `_request()`, which
merges them **inside** `send()` over the auth base. Merging inside `send()` is
required, not stylistic: the 401 path re-logins and retries, and a headers dict
built by the caller before the retry would resend the expired token. The merge
also means `If-Match` survives the retry, which is what the revision guard
depends on.

`scripts/test-mcp-401-retry.py` gained CASE 5, which drives the real call shape
and asserts both that `If-Match` reaches the transport on **both** attempts and
that the retry carries the refreshed token. 20/20 assertions pass.

## 4. API / MCP / tool wiring

### 4.1 What is correct

The router splits cleanly: `/health`, `/build-info`, `/api/auth/login` and
`/api/auth/register` are public; everything else sits below the JWT middleware
and the SOUL resolver. The transport body cap is raised to
`max_upload_mb + 14` MB so the handler's own 50 MB check governs — Axum's 2 MB
default would abort an oversized multipart upload with a broken pipe before the
handler ever ran.

The MCP server exposes 19 tools over `streamable-http` on `:8000/mcp`. Two
behaviours that look like failures and are not:

- `tools/list` without a session returns **400 "Missing session ID"** — correct
  protocol behaviour;
- SSE responses split the payload across multiple `data:` lines, so a parser
  reading only the first line reports **0 tools**.

The 401 re-login path retries **exactly once** and only when credentials exist;
a `PACGATE_JWT_TOKEN`-only deployment surfaces the 401 instead of looping.
Multipart uploads keep httpx's generated boundary — forcing
`application/json` there would make the server parse a multipart body as JSON.

The nginx timeout chain is consistent: `/pacgate/` 720 s read/send, `/` and
`/research/` 3600 s, `/version` 5 s. `SANITIZE_TIMEOUT_S` defaults to 700 s,
which stays under the 720 s proxy timeout.

### 4.2 Defect — `kb_search` ignored the caller's tenant (MEDIUM-HIGH, fixed)

`kb_search` took no `Extension<Claims>` and resolved the tenant from
`state.config.default_tenant` (a slug, resolved through the tenant store). Every
other matter-scoped handler uses `claims_to_ids`. In any deployment that is not
single-tenant, a token from tenant A searched tenant B's chunks.

**Fix.** `kb_search` now takes `Extension<Claims>` and derives the tenant from
the JWT via `claims_to_ids`, matching the rest of the surface. The
`default_tenant` fallback was removed rather than kept: the comment explaining it
("`PACGATE_DEFAULT_TENANT` is a slug, not a UUID") justified the *resolution*,
not the *bypass of claims*.

`search`, `list_connectors`, `list_registry`, `list_dd_configs` and
`search_health` remain claims-free. That is defensible — they read external
connectors and static catalogs, not tenant data — but it is an inconsistency
worth knowing about.

### 4.3 Defect — `kb_search` misreported each result's `data_level` (MEDIUM, fixed)

The response set `data_level: max_dl.code()` — the **filter ceiling**, not the
chunk's level. `KbSearchResult` had no `data_level` field at all, so the true
level was never selected. A T1 chunk returned under `max_data_level=T3` was
labelled `T3`, misstating classification to the review panel and to audit.

**Fix.** `KbSearchResult` gained a `data_level: DataLevel` field; both
`semantic_search` and `keyword_search` now select `c.data_level`; the handler
reports `r.data_level.code()`. An unparseable level decodes to
`T4SpecialSensitive` — the most restrictive value — so a corrupt row cannot
under-report its own sensitivity.

### 4.4 Defect — `compose.bundle.yaml` MCP service was under-configured (MEDIUM, fixed)

Against `compose.prod.yaml`, the bundle lane's `pacgate-mcp` service had:

| Setting | prod | bundle (before) |
| --- | --- | --- |
| `PACGATE_MCP_TIMEOUT` | `"700"` | `"60"` |
| `PACGATE_MATTER_ID` | set | **absent** |
| `../pacgate-mcp/server.py` mount | present | **absent** |

`install.ps1` uses `compose.prod.yaml`, so this was latent rather than live —
but the bundle file's own usage header invites running it directly, and doing so
would have produced a 60 s MCP timeout (killing every sanitize call, whose NER
pass runs for minutes), no default matter for the memory tools, and no
sanitize-timeout override.

**Fix.** All three now match prod. Verified with
`docker compose -f compose.bundle.yaml config`, which resolves
`PACGATE_MCP_TIMEOUT: "700"`, `PACGATE_MATTER_ID`, and the `server.py` mount.

### 4.5 Defect — the MCP fix would never reach an updated machine (HIGH, fixed)

This one was found while answering "how do other machines pick up these
verdicts", and it is the most consequential of the set.

`deploy/pacgate-mcp/server.py` is **bind-mounted** over the image's copy
(`compose.prod.yaml:444`, the `SANITIZE_TIMEOUT_S` override). Python imports its
modules at process start with no hot reload. `install.ps1 -Update` step 7c
restarts the services whose code is bind-mounted — and it restarted
`deer-flow` and `deer-flow-frontend` but **not `pacgate-mcp`**.

Consequence: the `PacgateApi.post()` `headers` fix (§3.2) would have looked
shipped on every updated machine while the running process still had the broken
signature. `pacgate_write_memory` would keep raising `TypeError` after a
successful update, with no error anywhere to say so. This is the same failure
class the step-7c comment already documents for `patches/*.py` and
`next.config.js` — the MCP service was simply missed.

**Fix.** Step 7c now restarts `pacgate-mcp` too, and
`scripts/audit-aipc-update-coverage.ps1` gained a `pacgate-mcp server.py` row so
the gate cannot drift again.

Verified, including a mutation test:

```
audit-aipc-update-coverage.ps1            13 of 13 covered, 0 gaps
  with the restart line renamed          12 of 13, GAP: pacgate-mcp server.py
```

The gate genuinely measures the behaviour rather than the comment: renaming the
`restart pacgate-mcp` call to `restart mcp-service` flips the row to GAP.

## 6a. How another machine picks these up

The fixes split into two delivery channels, and conflating them is how a fix
looks shipped while being inert.

| Fix | Ships as | Reaches a machine via |
| --- | --- | --- |
| `sanitize.rs` T4 hold | **compiled into `pacgate-api`** | new image tag + `compose pull` + recreate |
| `search.rs` tenant scope | **compiled into `pacgate-api`** | same |
| `pacgate-rag` `data_level` | **compiled into `pacgate-api`** | same |
| `server.py` `headers` fix | **bind-mounted file** | `git pull` + **`restart pacgate-mcp`** |
| `compose.bundle.yaml` env | **compose file** | `git pull` + `up -d` (config change forces recreate) |
| `install.ps1` step 7c | **installer script** | `git pull`, then `.\install.ps1 -Update` |

The three Rust fixes are **not** in the published `0.2.1` images — `v0.2.1` was
tagged at `a0003f8` (2026-10-22 14:39) and these changes are uncommitted on top
of `ad1da71`. A machine running `0.2.1` today has the T4 auto-pass, the
cross-tenant `kb_search`, and the misreported `data_level`. Shipping them needs
a version bump and a tag push (`build-ghcr.yml` triggers on `v0.2.*`).

The `server.py` fix needs no new image: it is bind-mounted, so `git pull` plus
the new step-7c restart is sufficient — which is exactly why the missing restart
in §4.5 mattered.

## 6b. Live proof on the HX370 stack (2026-10-22)

The audit's gate tests assert source shape. They do not prove a real job against
Postgres. So the fixes were released and then proven on the running stack, which
was on `0.2.1` (revision `a0003f8`) and therefore still had every bug.

**The bug, reproduced on 0.2.1:**

```
POST /pacgate/api/documents/{id}/sanitize  {"data_level":"T4"}
  -> verdict=pass  allow_auto_pass=False  require_human_review=True  chunks_promoted=1
GET  /pacgate/api/documents/{id}/download
  -> 200, 56 bytes
```

`allow_auto_pass=False` and `chunks_promoted=1` in the same response is the
defect stated plainly: policy refused, the code promoted anyway, and the most
sensitive document class was downloadable.

**The fix, on 0.2.2 (revision `ddbb70e`):**

```
POST /pacgate/api/documents/{id}/sanitize  {"data_level":"T4"}
  -> verdict=pass  allow_auto_pass=False  require_human_review=True  chunks_promoted=0
GET  /pacgate/api/documents/{id}/download
  -> 409
GET  /pacgate/api/kb/search?matter_id=...&q=process
  -> the held T4 document is absent
```

**The control — T3 must still release:**

```
POST /pacgate/api/documents/{id}/sanitize  {"data_level":"T3"}
  -> verdict=pass  allow_auto_pass=True  chunks_promoted=1
GET  /pacgate/api/documents/{id}/download
  -> 200
```

The control is the load-bearing half. A hold that never releases is as broken as
an auto-pass, just in the other direction, and only the T3 case distinguishes
"correctly held" from "everything stuck".

**MCP memory write, proven through the client:**

```
POST /api/matters/{id}/memory  If-Match: 0  -> 409 "file is at 1, caller expected 0"
POST /api/matters/{id}/memory  If-Match: 1  -> 200 {"revision": 2}
```

Before the fix both raised `TypeError: PacgateApi.post() got an unexpected
keyword argument 'headers'`. The revision guard was unreachable from MCP.

all five images public with `org.opencontainers.image.revision=ddbb70e` and
`version=0.2.2`.
