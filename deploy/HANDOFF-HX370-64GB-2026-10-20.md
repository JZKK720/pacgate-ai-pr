# Handoff: deploy Pacgate-ai 0.1.34 to the HX370 / 64 GB machine

**Audience:** an engineer with the HX370-64GB box in front of them.
**Source of truth:** `origin/main` - which pins the published `0.1.34` images.
**Goal:** a full, working stack - deer-flow (pacgate build), pacgate-api,
pacgate-mcp, qm-pacgate, OpenViking, OCR - verified by the repo's own gates.

Do not copy files from the 128 GB dev box. Everything below pulls from GitHub.

> **Clone `main`, not the tag.** `v0.1.34` identifies the published images, but it
> was cut before the pre-flight script and this document existed - a checkout of
> the tag has neither. `main` is only doc/PDF/new-script ahead of that tag, pins
> the same `0.1.34` images, and the provenance gate proves those are still exactly
> the artifacts clients pull. If you are asked to prove what is running, the
> answer is: images `8adb4818e7e5`, from tag `v0.1.34`.

## 0. What this machine is expected to detect

`install.ps1` picks a residency tier from **OS-visible** memory *and* VRAM:

| OS-visible RAM | VRAM | Tier | ctx | max loaded models |
|---|---|---|---|---|
| >= 56 GiB | >= 24 GiB | `high` | 65536 | 3 |
| >= 56 GiB | < 24 GiB | `big-ram-small-vram` | 32768 | 2 |
| 24-55 GiB | any | `standard` | 32768 | 2 |
| < 24 GiB | any | `constrained` | 16384 | 1 |

A **64 GB host with the 16 GB RX 7600 XT lands in `big-ram-small-vram`** - 2
resident models, 32768 ctx. That is deliberate: system memory decides whether
Ollama stays healthy, VRAM decides how many model instances fit, and the third
model has nowhere to live on a 16 GB card.

**Watch for this on the HX370:** the dev box is documented as "128 GB" but Windows
only exposes **31.65 GiB**, because the iGPU's fixed UMA carve-out (96 GiB) is
taken before the OS boots. If the HX370 shows far less than 64 GiB to Windows,
that is the same mechanism and the tier reflects what Windows sees, which is
what Ollama actually binds against.

## 1. Prerequisites

- Windows with Docker Desktop (WSL2 backend), daemon running
- **Ollama** desktop app installed
- `git`
- `python` on PATH (only used to *read* the Ollama app's context setting - the
  installer never writes it)
- The **Ollama account signed in** (`ollama signin`). The main model is
  `deepseek-v4.1-flash:cloud`, which routes through ollama.com and carries no
  local weights.
- Network access to `github.com` and `ghcr.io`

## 2. Clone and configure

```powershell
git clone https://github.com/JZKK720/pacgate-ai-pr.git C:\pacgate-ai-pr
cd C:\pacgate-ai-pr
# main, NOT `git checkout v0.1.34` - the tag predates the pre-flight script and
# this document. `main` pins the same published 0.1.34 images.
git log --oneline -1
```

Confirm the pins before you go further - these five lines are what will actually
be pulled:

```powershell
Select-String -Path deploy\client-bundle\compose.prod.yaml -Pattern 'image: ghcr.io/jzkk720'
```

Expect all five at `:0.1.34`.

Create the environment file - **the installer requires it and will not create it**:

```powershell
cd deploy\client-bundle
copy .env.example .env
```

Now edit `.env` and fill in these. Generate real values; the `change-me` strings
are placeholders and the installer rejects nothing, so a lazy copy ships a weak
password.

| Key | How to generate |
|---|---|
| `PACGATE_DB_PASSWORD` | `openssl rand -hex 16` (or any strong string) |
| `PACGATE_JWT_SECRET` | `openssl rand -hex 32` |
| `PACGATE_API_PASSWORD` | strong string - used by deer-flow and pacgate-mcp |

Leave `PACGATE_SETUP_TOKEN` blank: the stack generates one per process and it is
read from `docker logs deer-flow`. Leave `OPENVIKING_ROOT_API_KEY` alone unless
you want a specific value - if it stays at `change-me` the installer warns and
**OpenViking will boot-loop on `/health 503`**, so treat that warning as a stop
sign, not noise.

Do **not** hand-edit `PACGATE_MODEL_MID` / `PACGATE_MODEL_LOW`. The installer
writes them; section 5 explains why.

## 3. Install

**Run the pre-flight first.** It is read-only - it starts nothing and changes no
setting - and it catches every cheap-to-fix failure before any container churn:

```powershell
pwsh -File scripts\preflight-install.ps1
```

It checks: prerequisites, the residency tier this machine will select (and why),
whether Ollama is signed in (the MAIN model is `:cloud`, so it needs to be),
whether `.env` has real values or leftover placeholders, whether all five images
are **publicly** pullable for this tag, and whether the stack's ports are busy.
It exits non-zero with `[FAIL]` lines if anything is a blocker.

```powershell
cd C:\pacgate-ai-pr\deploy\client-bundle
.\install.ps1
```

Use `pwsh` if available, otherwise built-in Windows PowerShell 5.1 - both are
supported and gated.

What it does, in order: checks Docker and Ollama, applies the residency tier
(step 2b), renders configs, pulls images and models, brings the stack up,
bootstraps the admin, provisions a matter, stages and starts qm.

## 4. What step 2b changes on this machine, and what it does not

It sets **user-level** environment variables (these tune the Ollama server):

```
OLLAMA_NUM_PARALLEL      = 2
OLLAMA_MAX_LOADED_MODELS = 2
OLLAMA_KEEP_ALIVE        = 15m
```

and restarts Ollama once so they take effect.

It **does not** change the machine-wide context setting. That belongs to the
operator, not to Pacgate, because Ollama on these machines is shared with other
tools. The installer only *reads* it and prints what it found.

---

## 5. Why context is pinned per model

Both `pacgate-api` and `deer-flow` talk to Ollama's **OpenAI-compatible**
endpoint, and that endpoint **ignores any per-request `num_ctx`** (verified: both
`options.num_ctx` and a top-level `num_ctx` were ignored and the model still
loaded at the machine-wide value). `/api/generate` honours `num_ctx`, but neither
client can use it.

So the installer creates two derived tags with `PARAMETER num_ctx` baked in:

| tag | from | ctx | resident |
|---|---|---|---|
| `pacgate-mid` | `ornith-1.5:9b` | 32768 | 6.12 GB |
| `pacgate-low` | `gemma4:12b-it-qat` | 32768 | 7.63 GB |

and records them in `.env` as `PACGATE_MODEL_MID` / `PACGATE_MODEL_LOW`. The
derived tags share the base models' blobs - **no extra disk**. The base tags keep
whatever context the machine already had, so other tools are unaffected.

To opt out (more memory, still works): delete the two tags and point those two
`.env` keys at `ornith-1.5:9b` / `gemma4:12b-it-qat`.

## 7. Rollback

Images are tagged, so rollback does not need a rebuild:

```powershell
cd C:\pacgate-ai-pr
git checkout 8adb481          # the 0.1.33 release commit; a tag checkout also works
cd deploy\client-bundle
.\install.ps1 -Update
```

**A detached checkout is left alone.** `install.ps1 -Update` refreshes the repo
by following a *branch*, so before 2026-10-20 a `git checkout v0.1.33` would have
been fast-forwarded straight back onto `main` - the rollback silently undid
itself while reporting success. Measured: that pull moved HEAD from `9af44db` to
`3b235ed`. It now detects the detached state, prints `Repo is pinned at <tag>
(detached) - leaving it alone`, and still updates the images.

The tree then stays at 0.1.33 while the containers run 0.1.33 images - which is
what a rollback is supposed to mean. To go back to following a branch:
`git checkout main`.

Note that 0.1.33 predates the fresh-install fixes, so it is only a safe rollback
for a machine that is **already installed**, not for a clean machine.

## 8. Known gaps at this handoff

Stated plainly so nobody discovers them the hard way:

1. **Nothing has run on an HX370 yet.** Model sizes and container footprint
   (~4.06 GiB for 15 containers) are measured on the dev box. The HX370's real
   Windows reservation and its 16 GB discrete-card behaviour are not measured.
   Section 6 is the step that converts arithmetic into validation.
2. **qm and OpenViking are digest-pinned vendor images.** They travel as config,
   not as builds, and they are refreshed by the stack, not by `-Update`'s image
   pull alone.
3. **The 0.1.34 images were published from this commit.** Confirm the build
   finished and all five images return 200 anonymously before relying on them -
   see section 9.

## 9. Confirm the images are public before you start

The client path assumes **no `docker login ghcr.io`**. Verify:

```powershell
pwsh -File scripts\check-ghcr-pull.ps1 -Targets `
  'pacgate-ai/pacgate-api:0.1.34', `
  'pacgate-ai/pacgate-mcp:0.1.34', `
  'pacgate-ai/deer-flow-pacgate:0.1.34', `
  'pacgate-ai/deer-flow-frontend-pacgate:0.1.34', `
  'pacgate-ai/ocr-service:0.1.34'
```

A 200 is good. A 401 means the package is still private, and flipping a
personal-account package to public is UI-only - the API `/visibility` route 404s
even with `write:packages`.
