## 2. LAYER 1 — pacgate-api

| Check | Result |
| --- | --- |
| `GET /pacgate/health` (public) | **200** `ok` |
| `GET /version` (nginx, staleness probe) | **200** revision `8adb4818e7e5…`, version `0.1.34` |
| `POST /api/auth/login` | **200** |
| Login response fields | `expires_in, role, soul_id, tenant_id, token, user_id` |
| `POST /api/auth/register` (must be refused) | **403** ✔ gate closed |
| `GET /api/matters` | **200**, 2 |
| `GET /api/workflows` | **200**, **222** |
| `GET /api/matters/:id/documents` | **200**, 0 |
| `GET /api/matters/:id/memory` | **200** `{"facts":[],"history":{},"revision":0,…}` |
| `GET /api/matters/:id/workspace` | **200**, 0 documents |

**Route-survey correction.** An early pass reported `/api/tenants`, `/api/users`,
`/api/connectors` as `404` and `/api/documents` as `405`. Those are **the correct
answers**, not defects — verified against the router in
`pacgate-ai/crates/pacgate-api/src/lib.rs:49-182`:

* there is **no** `GET /api/tenants` — tenancy is a column, not a collection route;
* there is **no** `GET /api/users` — user creation is `POST /api/auth/users`
  (admin-only), listing is `GET /api/auth/me` for self;
* **no** `GET /api/connectors` — it is `GET /api/search/connectors`;
* `GET /api/documents` is `405` because `/api/documents` is registered **`POST`
  only** (upload); reads are `/api/documents/:id` or the matter-scoped
  `/api/matters/:id/documents`.

**Two client-side traps worth recording**, because both look like product
failures and are not:

1. The token field is **`token`**, not `access_token`. Reading `access_token`
   yields an empty bearer and turns every authenticated route into `401`.
2. `pacgate-api` publishes no host port; it is reached through nginx at
   `/pacgate/`.

## 3. LAYER 2 — pacgate-mcp

Reachable only at `http://pacgate-mcp:8000/mcp` on the compose network. Probed
from inside `deer-flow` (which has `python3`; `pacgate-api` does not).

| Check | Result |
| --- | --- |
| `POST /mcp` `initialize` | **200**, `Mcp-Session-Id` returned |
| server identity | **`pacgate` 1.30.0**, protocol `2024-11-05` |
| `notifications/initialized` | **202** |
| `tools/list` (with session) | **200 — 19 tools** |
| `GET /health`, `GET /` | **404** (no such routes; `/mcp` is the surface) |

**19 tools, matching the 19 recorded when 0.1.24 was audited (plan 026):**

`pacgate_kb_search`, `pacgate_connector_search`, `pacgate_list_connectors`,
`pacgate_list_matters`, `pacgate_read_memory`, `pacgate_write_memory`,
`pacgate_list_documents`, `pacgate_get_workspace`, `pacgate_read_document`,
`pacgate_upload_document`, `pacgate_list_workflows`, `pacgate_get_workflow`,
`pacgate_execute_workflow`, `pacgate_convert_document`, `pacgate_ocr_document`,
`pacgate_ocr_batch`, `pacgate_sanitize_document`, `pacgate_verify_sanitized`,
`pacgate_sanitize_text`.

`resources/list` and `prompts/list` both return empty arrays — correct for a
tools-only server.

⚠ **Two measurement traps this audit hit, both of which produced a false
"the product is broken":**

* A bare `tools/list` with **no session** returns
  `400 {"code":-32600,"message":"Bad Request: Missing session ID"}`. That is a
  *correct protocol reply* proving the server is alive; it is not a failure.
* The MCP server answers with **SSE** (`event: message` + `data:` frames), and
  the JSON is split across multiple `data:` lines. A parser that reads only the
  first `data:` line finds nothing and reports **0 tools**. The real count is 19.

## 4. LAYER 3 — deer-flow-pacgate + frontend

| Check | Result |
| --- | --- |
| `GET /` (frontend via nginx) | **200**, branded (47 files reference pacgate) |
| `GET /api/v1/auth/initialize` | **405** (route exists, POST-only) |
| `POST /api/v1/auth/login/local` | **200** + session cookie |
| `POST /api/threads` with session | **403 (cross-site guard)** — see below |
| live `storage_class` | **`pacgate_deerflow_adapter.storage.PacgateMemoryStorage`** ✔ |
| MCP servers wired | **3** (`openviking` + `pacgate` + `officecli`) |
| tiktoken encoding | **char-based fallback active** — see §6 |

**deer-flow ships uninitialized.** Its identity store is separate SQLite, so the
installer's pacgate admin does not log in here. First-run path, verified:

1. `POST /api/v1/auth/initialize` requires a **one-time setup token**.
2. The token is generated when `PACGATE_GENERATE_SETUP_TOKEN=1` (which compose
   sets when `.env`'s `PACGATE_SETUP_TOKEN` is blank) but is **only logged on the
   first call that actually reaches the gate** — i.e. a *valid* body. A `{}` body
   returns `422` before the token is ever emitted, so an operator who tries the
   obvious thing sees no token at all.
3. With the token, `201` + admin created; then login works.

**`/login/local` consumes `application/x-www-form-urlencoded`, not JSON.** It is
declared as `form_data: OAuth2PasswordRequestForm = Depends()`
(`/app/backend/app/gateway/routers/auth.py:418`). Posting JSON yields
`422 {"loc":["body","username"],"input":null}` because there is no form body.
`scripts/run-benchmark.ps1:155` works because PowerShell renders a bare hashtable
as form data.

⚠ **`POST /api/threads` returns 403 even with a valid session cookie.** The
`Origin` allowlist (`GATEWAY_CORS_ORIGINS`) is configured correctly for
`http://localhost:8089`, so this is a header/session nuance rather than a
misconfiguration — but it means a plain REST client cannot drive a thread. It
does **not** affect the smoke or benchmark lanes, both of which pass.

```
Cannot convert 'System.Security.SecureString' to 'System.Security.SecureString'
  $plainPassword = [System.Runtime.InteropServices.Marshal]::Pt...
```

**I could not reproduce this in isolation.** Under the same Windows PowerShell

## 8. Findings, ranked

### F1 — A gate can "pass" while testing the wrong service *(gate defect, medium)*

`scripts/test-lane-connectivity.ps1:198-206` (E2, the pacgate-mcp lane) probes
host ports **8090, 8091, 8088** for `/` or `/health`. On this stack:

* **`pacgate-mcp` publishes no host port** (`8000/tcp` only), so none of those
  ports can reach it;
* **port 8090 is `deer-flow-frontend`**, which answers `/` with **200**.

So E2 passes by talking to the frontend and reports
`reachable on port 8090/ (HTTP 200)`. The MCP server could be dead and E2 would
stay green. This is the same class as the E10 5.1 bug fixed in `a43d87c`: a
cross-layer gate whose pass does not imply what its name claims.

*Suggested direction:* probe `http://pacgate-mcp:8000/mcp` from a container on the
compose network and require a protocol-level response, rather than a host-port
`200`.

### F1b — `test-skills-and-templates.ps1:151` dies under PowerShell 5.1 *(gate defect, medium)*

```
docker : template parsing error: template: :1: unexpected "|" in command
  $mounted = docker inspect $qmCore[0] --format '{{range .Mounts}}{{"|"}}{{end}}'
```

The Go template contains `|`, which Windows PowerShell 5.1 mangles before docker
sees it — the **same bug class `a43d87c` fixed for E10**. It is a live-mount
*reporting* step, yet it takes the whole gate down.

**Note the inversion this creates:** the branch only runs when `qm-pacgate-core`
is up. So this gate **passed while qm was stopped** (the live check was skipped),
and turned red the moment qm was started. A gate that is green only because its
subject is absent is worse than no gate.

### F2 — `deer-flow` ships uninitialized, and the setup token is hard to discover *(UX, medium)*

The installer provisions the pacgate admin but not deer-flow's own admin. The
token is emitted only after a *valid* `/initialize` body, so the natural first
attempt (`{}`) returns `422` and logs nothing. An operator following
`.env.example`'s "search for `PACGATE SETUP TOKEN`" finds nothing and has no
signal that the gate is armed at all.

### F3 — `/login/local` is form-encoded, and the token field is `token` *(documentation, low)*

Both are correct server-side behaviour and both cost this audit a false negative
(422s, then a wall of 401s). `.env.example` and the benchmark script get it right
implicitly; nothing states it for a new client author.

### F4 — `tiktoken` cannot load and silently degrades token accounting *(environment, low)*

```
Failed to load tiktoken encoding 'cl100k_base'; falling back to char-based estimation
SSLError ... host='openaipublic.blob.core.windows.net' ... UNEXPECTED_EOF
```

The container cannot reach the tiktoken blob host. It degrades gracefully to
character-based estimation, so nothing breaks — but token counts (and therefore
`max_tokens` budgeting in `MemoryConfig`, which has a hard 2048 cap) are less
accurate. Expected on this box because the system proxy is dead; a client AIPC
with working egress should not see it.

### F5 — `setup-qm.ps1:208` SecureString crash *(unreproduced, low)*

Seen once, not reproducible in isolation under the same PowerShell 5.1. Recorded
so it is not lost; not claimed as a defect.

### F6 — Mutation gates leave the tree dirty on failure *(operational hazard, high)*

Carried forward from plan 027 and re-checked here (`CLEAN` this time). When
`test-*-mutations.ps1` fails, the restore never runs and **tracked product files
stay mutated** — observed twice: `.env.example`'s `PACGATE_MATTER_ID` blanked, and
`deer-flow-config.yaml`'s `storage_class` reverted to
`deerflow.agents.memory.storage.FileMemoryStorage`, i.e. the *unsanitized* memory
fallback the gate exists to prevent. Because those files feed other gates, one
mutation failure manufactures several unrelated red gates.

**Rule: after any `run-all-checks.ps1`, run `git status --porcelain
deploy/client-bundle/` and `git checkout --` any mutation before trusting a
result.**
