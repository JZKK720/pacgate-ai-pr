Probe: `委托人张三丰，身份证号110101199003072316，联系电话13800138000。`

Result: `verdict=pass`, **redaction_count=3**, `require_human_review=false`.

```
委托人[PERSON_9F82E227_1]，身份证号000000000000000026，联系电话[CN_MOBILE_9F82E227_3]。
```

- `张三丰` -> `[PERSON_...]` - **NER tier**. Rules alone cannot catch this name.
- `110101199003072316` -> `000000000000000026` - Luhn-valid, format-preserving mask.
- `13800138000` -> `[CN_MOBILE_...]`

The NER model is **baked into the image**, not volume-mounted: `/app/models/ner`
holds `model.safetensors` at 406,763,404 bytes plus config, vocab and
`SHA256SUMS`, and `PACGATE_NER_MODEL_DIR=/app/models/ner` is set in both base
compose files. This is the stronger arrangement - the weights cannot be lost to a
missing volume - and it is why the e2e gate's `ner weights mounted: False` line is
an artifact of that gate probing for a *volume*, not a redaction failure. The
redaction itself is asserted above and by
`test-sanitizer-e2e.ps1` (PASS, both identifiers removed from every `kb_chunks`
row, restore refused for attorney role, admin restore returns originals, ledger
and audit rows written).

## 10. Defects found and fixed

### 10a. A binary artifact download returned HTTP 500

`GET /api/threads/{id}/artifacts/mnt/user-data/outputs/<name>.pdf` failed with
`500 Internal Server Error` for every PDF deliverable. The traceback:

```
File "/app/backend/app/gateway/routers/artifacts.py", line 227, in get_artifact
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xa1 in position 11
```

`is_text_file_by_content()` decides "is this text?" purely by looking for NUL
bytes. A PDF header is printable ASCII (`%PDF-1.7`) and contains no NUL in its
first 8 KiB, so a **binary PDF was classified as text**, and the next line called
`read_text(encoding="utf-8")` with no guard. It died at byte 11 - immediately
after the header - and returned 500 instead of the file.

This is a client-facing defect: the generated `.docx`/`.pdf` deliverables a lawyer
asks for were listed by `GET /outputs` (HTTP 200) but could not be downloaded. The
listing working while the download fails is the worst shape of this bug, because
everything looks healthy until the user clicks.

Fixed in `deploy/client-bundle/patches/deer-flow-artifacts.py` (the same router,
bind-mounted over `/app/backend/app/gateway/routers/artifacts.py`). The correct
pattern already existed 30 lines above in the skill-archive branch - try decode,
fall back to raw bytes - so the fix reuses it rather than inventing a policy. The
same unguarded `read_text` on the `text/*` MIME branch was fixed too: a CJK `.csv`
saved as GBK would have raised the identical 500.

**Verified:**

| Check | Before | After |
|---|---|---|
| PDF artifact (1,814,947 bytes) | **500** | **200**, `application/pdf` |
| `.md` artifact (32,943 bytes) | 200 | 200, still `text/markdown` (no regression) |
| CJK `.md` artifact (20,744 bytes) | 200 | 200, still `text/markdown` |
| `test-chat-artifact-durability.ps1` | 1 of 5 FAILED | **7 of 7 PASS** |

The text cases matter as much as the PDF: the fix must not turn every UTF-8
document into an octet-stream download.

### 10b. `test-mcp-tool-surface.ps1` reported a false FAIL under Windows PowerShell 5.1

The gate parses the MCP `tools/list` payload out of a string and asserted
`$asserted.Count` against the declared set using:

```powershell
$actual = @($m.Groups['j'].Value | ConvertFrom-Json)
```

Windows PowerShell 5.1's `ConvertFrom-Json` does **not** unroll a JSON array into
the pipeline - it returns the whole array as one object - so the collection had
one element that was itself the `Object[]`. Measured on this box:

| Shell | `@('["a","b","c"]' \| ConvertFrom-Json).Count` |
|---|---|
| `powershell.exe` 5.1.26100 | **1** |
| `pwsh` 7.6.9 | **3** |

The consequences were exactly the failure mode this suite warns about:

- Under 5.1 the gate reported **4 FAIL** against a perfectly healthy stack, and
  the drift message read `advertised but not in the source: System.Object[]`.
- It passed in `run-all-checks.ps1` only because that runner prefers `pwsh` 7.
  A client AIPC with just 5.1 - the shell the client bundle is written for -
  would have seen a red gate on a correct install.

Fixed with a `ConvertFrom-JsonArray` helper that uses `ForEach-Object` to unroll
under both shells, applied at all three parse sites.

**Verified:**

| Check | Result |
|---|---|
| Clean source, `powershell.exe` 5.1 | 6/6 PASS, exit 0 |
| Clean source, `pwsh` 7 | 6/6 PASS, exit 0 |
| Mutation (source declares 20, server serves 19), both shells | **5 passed, 1 failed, exit 1** |
| Drift message readability under 5.1 | `missing from the running server: pacgate_mutation_probe_tool - …` |

The mutation test is the important one: the fix makes the gate shell-portable
without making it unable to fail. A sweep of every other `ConvertFrom-Json` site
in `scripts/` (43 remaining) found no other place that treats a parsed JSON
**array** as a collection, so this was the only instance of the pattern.

This is the third entry in the `DEFECT-ps51-*` class (`test-ps51-native-stderr.ps1`
covers the two redirection defects from 2026-10-27/28). The gate is *not* yet on
that file's watched list, because its remaining `2>&1` site is inside a
`$ErrorActionPreference = 'Continue'` script where it is safe on both shells;
adding it there would require routing through `Invoke-WithNativeStderr`, which
does not support the piped-stdin form this gate needs.

## 11. Regressions

**None remaining.** All 55 suite gates and all 19 reachable smoke assertions pass.

Two things that looked like regressions and were not:

1. **`test-chat-artifact-durability.ps1` failed after routine cache cleanup.** It
   had passed 7/7 earlier in the same day. The failure was not caused by the
   cleanup - the gate samples threads with `find`, and removing a stale agent
   `.venv` changed the ordering so it sampled a thread whose deliverable is a PDF.
   That exposed defect 10a, which had been latent on every PDF deliverable and had
   simply never been sampled before. Deleting the `.venv` removed no artifact; the
   PDF and all 50 source files in that workspace are intact.
2. **`test-mcp-tool-surface.ps1` failed standalone under 5.1** - the defect fixed
   in section 10b. It was never a product fault: `tools/list` returned exactly 19
   tools with descriptions and schemas the whole time.

Three things that are correctly *not* failures:

1. **`audit-deer-flow-patches.ps1` reports CANNOT CHECK** - its prerequisite is a
   gitignored deer-flow source checkout, which this box does not have.
2. **`smoke-full-stack.ps1` skips 2 assertions** - the deer-flow agent->MCP
   invocation needs a committed agent-run E2E that does not exist, and the
   openviking MCP probe needs the root key in env. Both are asserted elsewhere in
   this report (section 4 measures the 35-tool binding and section 6 exercises
   pacgate tool calls live).
3. **A 470 MB `checkpoints.db-wal`** was observed next to the 1.8 GB
   `checkpoints.db`. That is an uncheckpointed WAL, not garbage - it needs
   `PRAGMA wal_checkpoint(TRUNCATE)` during a quiet window, never a file delete.

## 11a. Disk retained on this box (cleanup pass)

The stack was measured at **2,900.7 MB** under `deploy/`. Almost none of it was
cache: `deploy/client-bundle/data/` is the deer-flow bind mount and is live
runtime state, not a build artifact. What was actually reclaimable:

| Item | Reclaimed | Basis |
|---|---|---|
| Stale agent `.venv` in a 2026-10-21 thread | **517 MB** | self-created venv, no writer since, no process referencing it (verified by a `/proc` cmdline scan) |
| `checkpoints.db-wal` truncate | **470 MB** | `PRAGMA wal_checkpoint(TRUNCATE)`, `busy=0`, `integrity_check = ok`, all 5,955 checkpoint rows and 8,570 writes intact |
| 6 `__pycache__` dirs in the repo tree | 0.19 MB | bytecode, regenerated on import |
| **Total** | **~987 MB** | `deploy/` 2,900.7 -> **1,913.2 MB** |

Deliberately kept: `node_modules` (2.3 MB - backs the running qm compose
working_dir), the 11 tracked `docs/` PDFs (1.1 MB of client-facing deliverables),
and every thread workspace with its files. No matter data, document or `kb_chunks`
row was touched - those live in Postgres, outside all of this.

The `.venv` deletion is what caused `test-chat-artifact-durability.ps1` to change
its sample and expose defect 10a. That is the value of the check: a green run
yesterday did not mean a green run today.

`scripts/clean-thread-workspaces.ps1` now bounds this growth going forward. It is
report-only by default, protects the newest N threads regardless of age, and
deletes through `DELETE /api/threads/{id}` so the directory, the `checkpoints`
rows and the `store` metadata cannot diverge. Verified on a throwaway thread:
after delete, 0 directories lacked a DB row. Documented in
`SETUP-AND-OPERATIONS.md` section 6.6 (EN + ZH).
